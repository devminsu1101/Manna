# 기도 중심 개편 계획 — 2026-11-23 방향 변경 반영

## 2026-11-23 방향 변경 — 공동체별 나눔과 응답

이번 결정은 **방향만 확정**한다. 구체적인 화면 구성·탭 이름·기능 세부 규칙·데이터 모델·구현 순서는 아직 정하지 않는다.

- 나눔은 공동체별로 유지한다. 여러 공동체의 글과 대화를 하나로 합치는 사람 중심 통합 피드 계획은 보류한다.
- 공동체는 진지한 이야기를 꺼내도 뜬금없지 않고, 다른 이야기가 올라온 뒤에도 그 글에 응답할 수 있는 공간을 지향한다. 댓글·반응으로 서로의 이야기를 읽고 답하는 경험을 우선한다. 공동체 간 대화를 합치지 않는다.
- 프론트 전반의 가독성과 일관성을 개선하는 방향으로 개편한다. 긴 글을 읽고 댓글·반응을 남기는 경험을 중요하게 보되, 구체적인 디자인과 화면 범위는 후속 논의에서 정한다.
- 챌린지·출석체크·공통 질문 기능·개인별 리마인드 알림은 이번 방향에 포함하지 않고 보류한다. 투표도 MVP에 포함하지 않는다.
- 기존 기도의 목적은 유지한다. 쉽게 접근해 서로를 위해 자주 기도하고, 기도제목을 나누며 기도받는 경험을 지향한다.

**이전 계획과의 관계:** 아래 2026-11-18 안의 사람 중심 피드, 여러 공동체 사본을 단일 글로 합치는 데이터 전환, 공동체 구분 없는 댓글·반응과 이를 전제로 한 공개 범위·스키마·API 설계는 현재 실행 기준이 아니다. 해당 전환 작업은 보류하고 후속 설계에서 재검토한다. 본문 길이·사진 수·반응 종류 등 기존 세부안도 이번 대화에서 재확정한 것으로 취급하지 않는다. 아래 내용은 당시 계획 기록으로 보존하며, 기도·설정 등 별도 항목을 이번 결정으로 취소하거나 완료 처리하지 않는다.


> 2026-11-18 기획 결정. 이 문서는 **다음 버전의 목표와 전환 순서**다. 현재 동작과 API는 `03_API_SPEC.md`, 현재 DB는 `apps/init-db.sql` 및 `06_ERD.md`의 기존 구조를 따른다. 기존 문서의 D-3507(방마다 별도 글), D-3610(공용 작성 화면), D-3604(공동체 홈), D-3630(방별 댓글·반응)은 구현 당시 기록이며, 이 개편의 목표에 적용하지 않는다.

## 확정된 사용자 경험

1. 앱의 첫 탭과 로그인 후 기본 화면은 **중보기도실**이다. 사람을 좌우로 넘기며 기도하는 현재 흐름과 사람 기준 `기도했어요`(하루 한 번)를 유지한다. 익명 기도실과의 상하 스와이프 분할, 기도문 전달 기능은 이번 범위에 넣지 않는다. 익명 기도제목 자체도 우선순위에서 내린다.
2. 하단 탭은 왼쪽부터 **기도 · 나눔 · 성경 · 마이** 네 개다. 가운데 `+` 탭과 공동체 홈 탭은 없앤다. 선택된 탭은 기존 그림의 본색과 명확한 상태 표시, 나머지는 같은 그림의 회색 처리로 구분한다. 새 이미지 파일은 필요 없다. 선택 상태는 색 외에도 텍스트·표시로 전달한다. 공동체 목록·가입·초대·관리 진입은 마이페이지 또는 관련 화면에서 유지한다.
3. **나눔**은 연결된 사람의 글을 읽는 블로그형 피드다. 한 번 올린 글은 한 편으로 저장하고, 선택한 모든 공동체에서 같은 본문·사진·댓글·반응을 본다. 작성자 이름·사진을 누르면 별도 공개 프로필 대신 그 사람의 기도 화면으로 간다. 마이페이지에는 내 글 피드와 내 기도제목 목록을 각각 둔다.
4. 나눔 작성과 기도제목 작성은 별도 폼·경로다. 나눔은 본문 최대 **10,000자**, 사진 최대 **1장**과 공개 범위를 입력한다. 피드는 긴 본문을 일부만 보여주고 상세에서 전체를 읽는다. 사진은 비율과 읽을 수 있는 화질을 유지하고 피드용 미리보기를 별도로 사용한다.
5. 나눔 한 편마다 댓글과 캐릭터 반응을 단다. 댓글은 작성자 본인이 삭제할 수 있다. 반응은 `hi | warm | tears | together` 중 사용자당 한 개이며 같은 반응을 다시 누르면 취소, 다른 반응을 누르면 교체한다. 댓글·반응 알림은 첫 버전에서 제외한다. 기도제목에는 적용하지 않는다.
6. 기도제목은 여러 개를 이력으로 보관하지만 **동시에 활성화되는 것은 최신 한 개**다. 새 제목을 올리면 이전 활성 제목을 비활성화하고, 옛 제목은 작성자 이력에 남긴다. 기도실에는 활성 제목만 보여준다. 별도 기도제목 폼으로 분리한다. 기도 횟수는 계속 사람 기준이며 제목 ID와 연결하지 않는다.
7. 마이페이지에 **설정** 진입점을 둔다. 알림 켜기·끄기, 업데이트 내역(패치노트), 로그아웃, 계정 삭제를 설정으로 옮긴다. 패치노트는 운영자만 별도 폼에서 작성·수정·게시하며 사용자는 설정에서 읽는다. 기존 관리자 읽기 기능은 유지한다. 계정 삭제 전 리더는 맡은 공동체를 위임하거나 삭제해야 한다.

## 나눔 공개 범위와 권한

- 작성 시 **연결된 공동체 모두** 또는 **공동체 선택**을 고른다. 선택 모드에서 고른 공동체 ID는 글에 고정한다. 나중에 작성자가 새 공동체에 가입해도 해당 글의 대상은 자동으로 늘지 않는다. 작성자는 글을 수정하면서 범위를 조정할 수 있다.
- 선택 모드의 독자는 **글에 지정된 공동체 하나 이상에서 작성자와 독자가 모두 현재 `active`**일 때만 볼 수 있다. 작성자 본인은 언제나 자기 글을 볼 수 있다. 공동체 탈퇴·강퇴·삭제 등으로 연결이 끊기면 독자는 글·사진·댓글·반응에 더 이상 접근할 수 없다. `pending`은 접근할 수 없다.
- **연결된 공동체 모두** 모드는 조회 시점에 양쪽이 함께 활동 중인 공동체로 범위를 계산한다. 이후 새 공동체에서 연결되면 과거의 이 모드 글도 보일 수 있으므로 작성 화면에서 이 차이를 분명히 설명한다.
- 과거 글을 옮길 때는 **원래 선택했던 공동체만** 공개 대상으로 저장한다. 현재 함께 활동하는 모든 공동체로 자동 확대하지 않는다. 기존 글의 여러 방 사본은 하나의 대표 글로 합치되 원래 각 사본이 걸렸던 공동체를 대상 집합으로 합친다. 글별로 다른 본문은 별도 검수한다.
- 권한 검사는 목록뿐 아니라 상세, 댓글·반응 조회/쓰기, 사진 전달, 이전 주소 리다이렉트에서 동일하게 적용한다. 접근할 수 없는 글은 존재 여부를 드러내지 않는다.

## 데이터와 API 목표

| 데이터 | 다음 버전의 역할 |
|---|---|
| `sharings`, `sharing_communities` | 기존 운영 데이터·옛 ID 대응을 위한 레거시. 새 글의 저장소로 쓰지 않는다. 검증 전 삭제하지 않는다. |
| `sharing_posts` | 나눔 한 편당 한 행. 작성자·본문(`TEXT`)·사진 참조·작성/수정 시각·공개 모드를 가진다. |
| `sharing_post_audiences` | 공동체 선택 모드에서 고른 공동체의 고정 집합. |
| `sharing_post_comments`, `sharing_post_reactions` | 방 구분 없는 글 단위 댓글·반응. 반응은 글/사용자당 하나. |
| `prayer_requests` | 기도제목과 활성 상태·이력. 작성자당 활성 한 건만 허용한다. |
| `patch_notes` | 운영자 작성 업데이트 내역. 임시 저장/게시 상태를 갖는다. `sharings`의 새 `type`으로 넣지 않는다. |

- 나눔 API는 글 하나를 생성하고 공개 범위를 함께 받는다. 피드는 **접근 가능한 글만** 최신순으로 페이지 단위로 조회한다. 작성자 자신의 글도 마이페이지에서 별도로 조회한다. 본문 최대 10,000자는 새 폼·서버 양쪽에서 검증한다. DB `TEXT` 자체는 길이 변경이 필요 없다.
- 기도제목 API는 생성 시 이전 활성 제목 비활성화와 새 제목 활성화를 **한 트랜잭션**에서 처리한다. 동시에 두 번 올려도 활성 제목이 두 개 생기지 않도록 DB 제약 또는 동등한 직렬화가 필요하다. 기존 기도실 조회·기도 기록은 사람 기준을 유지한다.
- 옛 `/sharings/{id}` 링크와 알림의 `linkPath`는 새 글로 이어지게 ID 대응을 보존한다. 모든 방 사본 ID가 같은 새 글로 가더라도 **새 권한 검사**를 먼저 거친다. 이전 기도제목 링크는 새 기도 이력/상세로 연결한다.
- 공개 범위가 바뀔 수 있으므로 게시 사진은 **Private Vercel Blob**에 저장하고 인증된 전달 경로에서 현재 접근 권한을 확인한다. 기존 프로필 사진용 Public Blob 규칙(400px·1MB)을 사진 나눔에 그대로 적용하지 않는다. 이미지 형식·용량 제한과 업로드 방식은 구현 전 실제 기기에서 정한다. 서버 함수 업로드 한계를 넘는 파일은 인증된 클라이언트 직접 업로드를 검토한다.
- 패치노트 API는 관리자 인증을 서버에서 확인한다. 사용자에게는 게시된 글만 준다. 패치노트 작성·표시는 나눔의 카드 모양 일부를 재사용할 수 있지만 데이터와 폼은 독립한다.

## 앱 시작 화면

- 현재 `/`는 화면을 그리기 전에 사용자 조회와 리다이렉트를 수행해 앱 실행 직후 빈 구간을 만들 수 있다. 새 `/`를 기도 홈으로 연결하면서, **첫 앱 실행의 로딩 구간**에는 브랜드 시작 화면을 보여 주고 실제 홈이 준비되면 제거한다. 탭 이동이나 기도실 재방문마다 시작 화면을 반복하지 않는다. 고정 시간 타이머나 가짜 진행률은 쓰지 않는다.
- OS가 PWA를 여는 동안 표시하는 시작 화면과 웹 문서가 로드된 뒤 표시하는 로딩 화면은 다른 구간이다. 현재 빈 구간이 어느 쪽인지 실기기 화면 기록으로 확인한다. Android 매니페스트 색·아이콘과 iPhone 홈 화면 동작을 각각 점검한다.
- 미로그인 사용자의 성경 진입, 로그인 뒤 초대 링크 복귀 쿠키, 직접 연 딥링크, 로그인 후 기도 홈 진입을 유지한다. 기존 고아 `/landing` 타이머 화면은 시작 화면의 근거로 사용하지 않는다.

## 운영 데이터 전환 순서

1. 운영 DB 백업과 건수·ID·공동체 연결·본문 차이 목록을 만든다. 서비스 이용 중이므로 쓰기 동결 또는 구버전/신버전 동시 대응 방식으로 전환 구간을 설계한다.
2. 새 테이블·권한 조회·옛 ID 대응을 먼저 배포하고, `daily`/`scripture` 사본을 대표 글로 묶는다. **본문이 같다는 이유만으로 다른 날의 별도 글을 합치지 않는다.** 생성 묶음과 각 공동체 연결을 대조한다. 2,000자 제한 때문에 이어 쓴 `…2` 글은 별개 글이다.
3. 운영 데이터에서 본문이 다른 묶음은 11개(두 버전 10개, 세 버전 1개)로 확인됐고, 그 글의 작성자 혜림은 **각 글의 마지막 수정본 A′를 대표로** 쓰길 요청했다. 다만 `updated_at`과 커밋 시각이 없어 어느 본문이 각 묶음의 마지막 수정본인지 ID만으로 단정할 수 없다. 후보를 수동 대조하고 애매하면 작성자에게 확인한 뒤 대표본과 근거를 기록한다. `xmin`은 보조 단서일 뿐 수정 시각이 아니다.
4. 옛 `prayer` 행을 `prayer_requests`로 옮긴다. 작성자별 최신 공개 제목만 활성화하고 이전 행은 이력으로 둔다. 한 사람의 여러 제목이 같은 시각이면 ID 등 결정 가능한 보조 순서를 정한다.
5. 원본/대상 건수, 작성자, 공개 공동체, 본문, 옛 링크, 읽기 권한, 새 글 작성/수정/삭제, 사진·댓글 권한을 검증한 뒤 앱의 읽기·쓰기를 새 테이블로 전환한다. `sharings` 원본과 ID 대응은 되돌릴 수 있게 보존한다.

## 작업 묶음과 확인 기준

1. **기반/전환:** 새 테이블·마이그레이션·옛 링크·접근 권한. 기존 글이 새 공동체에 노출되지 않는지 확인.
2. **기도 홈:** `/` 및 네비 개편, 빈 화면 계측과 시작 화면, 집중 모드·좌우 스와이프·초대 복귀·비로그인 성경 확인.
3. **기도제목:** 독립 폼, 활성 한 건, 이력, 새 글 작성 시 전환, 기존 사람 기준 기도 기록 확인.
4. **나눔:** 단일 글·공개 범위·피드·내 글·사진·댓글·반응. 가입/탈퇴/강퇴/범위 수정 직후의 접근 재검사와 긴 글 표시 확인.
5. **설정/운영:** 설정 진입, 알림 토글 이동, 패치노트 게시·조회, 로그아웃, 리더 위임/삭제를 포함한 계정 삭제와 데이터 정리.

## 구현 전에 남은 세부 결정

- 나눔 사진의 허용 형식·최대 용량과 긴 본문의 피드 미리보기 길이.
- 과거 본문이 다른 11개 묶음에서 각 **마지막 수정본을 식별하는 일**. 사용자 의사는 확인됐으나 DB에 수정 시각이 없어 자동 규칙만으로 단정할 수 없다.
- 패치노트 목록의 읽음 표시·푸시, 기도제목 비활성/재활성 관리 UI, 익명 기도실, 기도문 전달, 자동 카카오 알림은 이번 범위 밖이다. 오래된 기도제목 안내는 당분간 운영자가 소수에게 직접 보낸다.
