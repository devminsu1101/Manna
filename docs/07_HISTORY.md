### 영역 1 — 성경 리더

**✅ D-101. 상단 헤더를 sticky로 두고 장 제목 밴드를 z-index로 덮는다**
- 왜: 헤더와 밴드가 둘 다 sticky면 밴드의 `top`을 헤더 표시 여부에 따라 토글해야 해서 모든 장 섹션에 스크롤 클래스가 붙는다. 헤더(z-30)가 밴드(z-20)를 덮으면 밴드는 `top-0`에 그대로 두면 된다(사용자 제안).
- 결과: 성공. 밴드가 헤더 밑으로 미끄러져 들어가고 배경(`bg-header`)이 같아 이어지듯 보인다.

**✅ D-102. 헤더의 장 숫자를 useState가 아니라 외부 스토어로 관리**
- 왜: 공통 조상에 useState로 두면 장이 바뀔 때마다 `ChapterFeed`가 리렌더되어 **이어 붙인 모든 절**이 다시 그려진다. `useSyncExternalStore`로 헤더만 숫자를 구독하면 O(1).
- 결과: 성공. `CurrentChapterProvider` 신설.

**✅ D-103. 이어읽기를 localStorage가 아니라 쿠키로**
- 왜: 서버에서 읽어야 `/bible`이 서버 리다이렉트로 이어읽고, `BottomNav`가 서버 컴포넌트로 남는다. 쿠키 값은 조작 가능한 입력이라 `getBook` + 장 범위로 검증(오픈 리다이렉트 방지).
- 결과: 성공. 조작 쿠키 14종 차단 확인.

**✅ D-104. 이전 장은 진입 시 DOM에 붙이고 위치를 한 번만 잡는다** (사용자 지시로 재설계)
- 왜: 처음엔 "스크롤이 이전 장을 부르고 → 붙으면 보정" 순서라 보정이 iOS 관성과 싸워 `/ps/43`이 41·42로 밀렸다. "직전 장은 DOM으로 불러오되 보이는 위치만 조정하라"는 지시로, 진입 시 스크롤 무관하게 한 장 붙이고 다 붙은 문서에서 위치를 한 번 잡게 바꿈.
- 결과: 성공. 주소=헤더=화면이 어떤 스크롤에도 일치.

**✅ D-105. 현재 장 판정 띠를 헤더 높이만큼 내린다**
- 왜: 판정 띠가 `상단 10%`(62.9px)였는데 헤더가 63px이라 **헤더에 완전히 가린 영역**을 보고 판정 → 화면엔 42편인데 헤더·주소는 41편. 원래 주석 "고정된 밴드와 같은 지점"은 헤더가 숨던 시절 전제였고, 헤더가 항상 뜨게 되며 깨졌다.
- 결과: 성공.

**❌ D-106(폐기). 이전 장 센티넬 마진을 다음 장과 대칭(600px)으로 두기**
- 왜 시도: 다음 장 프리페치와 대칭이 자연스러워 보였다.
- 실패 이유: 진입 즉시 이전 장을 당기고, 시편처럼 장이 짧으면 연쇄로 당기며 매번 스크롤 보정이 필요했다. iOS 관성 중 프로그램적 스크롤이 무시되면 밀렸다. → D-104로 대체.

**⚠️ D-107. `next start`/헤드리스로만 검증한 것의 한계**
- 초기 리더 이슈들을 Chromium 헤드리스로만 검증했는데, iOS 모멘텀·Safari 고유 동작(scroll anchoring 없음)은 재현이 안 됐다. 실기기(WebKit/실 Safari) 확인이 최종 기준임을 반복 학습.

### 영역 2 — 성경 데이터 소스 (실패한 소스들 분리)

**❌ D-201(폐기). 개역한글 `thiagobodruk/ko_ko.json`**
- 왜 시도: 원래 앱에 들어 있던 소스.
- 실패 이유: 데이터가 손상. 27/66권에서 장 끝 절이 잘려 **155절 누락**, 욥기는 **36장이 통째로 빠져 이후 장 번호가 하나씩 밀림**(“욥기 38장”을 열면 실제 39장), 42장은 빈 장.

**❌ D-202(폐기). getbible 개역성경**
- 왜 시도: 개역한글 대체 후보. 장은 온전했다.
- 실패 이유: 사본 생략절(막 9:44 등)을 **지우고 번호를 당겨** 같은 종류의 오류를 새로 만들었다. `?`·`!`·인용부호도 전무.

**✅ D-203. 개역개정 `bible.json` 채택 (번역본 교체)**
- 왜: 66권/1189장 완전, 빈 장 0, 생략절 13곳을 `(없음)`으로 정확히 표기, 행 24:7 부재도 정본과 일치. `elroi773/bible-api`는 188절짜리 랜덤 구절 API라 후보 탈락.
- 결과: 성공. 번역본이 개역한글→개역개정으로 바뀜(사용자 승인).
- 부수: `요18:이` 파싱 사고(절 번호 자리에 본문 “이”가 들어감) 1건 복원. 합본 절 11곳(신 6:18-19 등)에 `endVerseNum` 도입.

**✅ D-204. NUL 패딩 제거를 빌드에서 강제**
- 왜: 원본이 3개 절(삿 21:25, 습 3:20, 벧전 5:14, 각 권 마지막 절)을 NUL로 패딩. 화면엔 안 보이지만 **Postgres text 타입이 NUL을 못 담아** 시드 적재가 통째로 실패. `\s`가 NUL을 안 걸러 `trim()`도 못 지운다.
- 결과: 성공. `normalize()`가 제어문자를 걷어내고, 남으면 빌드가 멈추는 가드 추가. **실제 Postgres에 부어보다 발견** — 생성만 하고 넘어갔으면 놓쳤을 것.

### 영역 3 — ERD / 스키마

**✅ D-301. 전체 도메인 ERD를 먼저 설계 (build-first 아님)**
- 왜: 메인 화면 하나가 기도·공동체·성경을 동시에 참조하고, 나눔이 여러 공동체에 크로스포스트되는 등 도메인이 얽혀 있어, 관계를 먼저 못 박지 않으면 나중에 테이블을 다시 잡게 된다.
- 결과: 성공. 임시 Postgres에 부어 시나리오 + 나쁜 데이터 13종 차단 검증.

**✅ D-302. 공동체는 계층 없이 평평** (사용자 결정)
- 왜: 카톡 단톡방처럼 생성 시 이름 짓고 모임장이 수정. 교회-지부-반 트리는 확정 요구가 아니라 `parent_id` 없이 이름 문자열로만.

**✅ D-303. 기도 카운트는 사람 기준 + 하루 하나** (사용자가 설계 중 수정)
- 왜: 처음엔 `prayer_logs`를 기도제목(sharing) 기준으로 잡았으나, 기도 상세의 "기도했어요" 버튼이 **사람 카드**에 하나 붙어 있음 → 제목 기준(좋아요식)은 인기 제목에 몰려 중보기도 취지에 어긋남. 키를 `(기도받는 사람, 기도한 사람, 날짜)`로 바꿈. sharing_id 미포함.
- 결과: 성공. 로그 테이블을 두는 이유 = "카운트만"으론 하루 집계도 집중모드 건너뛰기도 불가.

**✅ D-304. 기도제목 = prayer 타입 나눔, 최신만 노출**
- 별도 prayers 테이블 없음(작성 화면이 나눔과 동일). `ORDER BY created_at DESC LIMIT 1`로 최신만.

**✅ D-305. PK는 SERIAL 유지** (사용자 결정) — 기존 성경 3테이블과 일관.

### 영역 4 — 인증 (Google OAuth)

**✅ D-401. Next 프록시 + Spring 세션 (JWT 아님)** (사용자 결정)
- 왜: 브라우저가 :3000만 상대하고 Spring(:8080)은 프록시 뒤 → 세션 쿠키가 first-party라 dev(http)에서 CORS·SameSite 문제 없음. `forward-headers-strategy=framework`로 프록시 뒤에서도 redirect_uri가 :3000으로 생성됨(검증).
- 결과: 성공. `/api/v1/me` 401, `/oauth2/authorization/google` 302(accounts.google.com)까지 검증.

**✅ D-402. Spring Boot 4 / Security 7 API를 문서·JAR로 확인하며 작성**
- 왜: 학습 범위(Boot 3 / Security 6) 밖. 메모리로 쓰면 위험.
- 결과: 성공(compileJava 통과). `spring-boot-starter-oauth2-client`가 의존성에서 **빠져 있어** 추가. `ddl-auto=validate`로 init-db.sql 스키마와 엔티티 일치 검증.

**✅ D-403. `/api/v1/me`를 rewrite가 아니라 Next 라우트 핸들러로**
- 왜: rewrite 프록시는 백엔드가 꺼져 있으면 매 요청 `ECONNREFUSED`를 로그에 도배(프론트만 개발할 때 흔함). 라우트 핸들러는 백엔드 다운 시 조용히 401.
- 결과: 성공. OAuth 경로(브라우저 리다이렉트)는 rewrite 유지.

**⚠️ D-404. CSRF 임시 비활성 (MVP)**
- 왜: 변경 API가 로그인/로그아웃뿐이라 위험이 낮고 로그아웃 POST를 단순화. `SecurityConfig`에 TODO.
- 주의: **v1.1 나눔·기도 쓰기 전 반드시 재활성.** 세션 쿠키 앱은 CSRF에 취약.

**⚠️ D-405. Google OAuth는 dev에서 localhost만.** 사설 IP(192.168.x.x)·비HTTPS 거부 → 폰(LAN IP)으로 로그인 불가, HTTPS(배포/터널) 필요. 실제 Google 로그인 end-to-end는 사용자만 검증 가능(헤드리스 불가).

### 영역 6 — Vercel 배포 (실패가 가장 많았던 구간, 분리 서술)

최종 원인은 하나였다: **Vercel 프로젝트의 `framework` 설정이 `null`** 이라 Vercel이 `@vercel/next`가 아니라 `@vercel/static-build`로 빌드 → `next build`는 돌지만 `.next`가 Next 앱으로 처리되지 않고 public 자산만 복사 + "모든 경로 404" 라우팅 생성 → 전 라우트 `x-vercel-error: NOT_FOUND`.

#### ❌ 실패한 시도들 (각각 왜 무효였나)

**❌ D-601. push하면 Vercel이 알아서 앱을 찾겠지**
- 실패 이유: 모노레포. Next 앱이 `apps/frontend/`에 있고 저장소 루트엔 `package.json`이 없어 프레임워크 미감지 → 404.

**⚠️ D-602. Root Directory = `apps/frontend` 설정**
- 필요조건이나 불충분. 빌드는 `apps/frontend`에서 돌게 됐지만, 초기 미감지로 잡힌 **`framework: null`이 그대로 남아** 여전히 정적 빌더 사용 → 404 지속.

**❌ D-603. Deployment Protection이 원인이라는 가설**
- 왜 시도: 배포 URL을 fetch하니 `vercel.com/sso-api`로 302 리다이렉트 → 인증 벽 확인.
- 실패 이유: 벽을 껐는데도 404. 그리고 사용자(계정 주인)가 데스크톱에서도 404. Protection은 **A 블로커였지 THE 404 원인이 아니었다.** 옛 프로젝트(빈 빌드)와 새 프로젝트(기본 Protection 켜짐)가 겹쳐 진단을 흐림. "Protection이면 전에도 됐어야지"라는 사용자 지적이 정확했음.

**❌ D-604. 대시보드에서 Framework Preset을 Next.js로**
- 실패 이유: 사용자가 설정했다는데 `vercel pull`로 확인하니 여전히 `framework: null`. 대시보드 설정이 이 케이스에선 저장/반영 안 됨.

**❌ D-605. `next build --webpack` (Turbopack이 원인이라는 가설)**
- 왜 시도: 빌드 로그의 `(Turbopack)`이 유일한 비표준 요소로 보여, Vercel이 Turbopack 프로덕션 출력을 서빙 못 한다고 추정.
- 실패 이유: 완전 헛다리. 실제 빌더가 `@vercel/static-build`였으니 Turbopack이든 webpack이든 무관. **불필요한 변경**(무해하지만).

**❌ D-606. 잘못된 URL 테스트**
- 실패 이유: 옛 프로젝트의 배포 해시 URL(`manna-7quu08tkq-…`)을 찍어 404를 봤는데, 그건 죽은 옛 배포였다. 진짜 프로덕션 별칭(`manna-five-tau`)이 따로 있었다.

#### ✅ 유효했던 결정적 실험/수정

**✅ D-607. 로컬 프로덕션 재현 (`next build && next start`)**
- 왜: 코드/빌드 vs Vercel 서빙을 가르는 실험.
- 결과: 로컬 프로덕션 서버에서 `/`·`/login`·`/landing` 전부 200 → **코드/빌드는 정상, Vercel 서빙이 문제**로 확정. 이걸 처음부터 했으면 D-603·D-605 헛다리를 안 짚었을 것.

**✅ D-608. `vercel build` 로컬 재현 + `.vercel/output` 해부**
- 왜: Vercel의 변환을 로컬에서 재현해 라우팅 config를 눈으로 확인.
- 결과: **근본 원인 발견.** `config.json`이 "모든 걸 404"만 담고 `functions/` 없음. diagnostics의 `builder.name: "@vercel/static-build"`, `framework: null`이 결정적 증거.

**✅ D-609. `apps/frontend/vercel.json`에 `framework: "nextjs"` 명시**
- 왜: 프로젝트 설정의 null을 **코드로 오버라이드**. 대시보드 설정이 안 먹었으니(D-604) 버전 관리되는 vercel.json이 더 확실.
- 결과: 성공. `vercel build` 재현 시 `@vercel/next` 사용 → config.json 라우트 35개 + `functions/` 생성. push 후 git 배포(57초, Ready, Production)가 정상 200.

#### 메타 교훈 (이 세션)
- **추측→재배포 루프가 최악.** 재배포는 피드백이 느리고 변수가 많다.
- **로컬 재현을 먼저.** `next start`(코드/빌드 확인) → `vercel build`(플랫폼 변환 확인)가 원격을 찌르기 전에 왔어야 했다.
- **증상(404)은 여러 원인을 가린다.** Protection·Turbopack·URL 혼동이 다 겹쳤다. 헤더(`x-vercel-error`)와 빌더 diagnostics 같은 **기계적 증거**로 갈라야 한다.

### 영역 7 — 구절 복사

**✅ D-701. 절 선택 후 동작을 '나눔하기'가 아니라 '복사하기'로** (사용자 결정)
- 왜: `ShareVerseButton`은 `onClick`이 없는 자리 표시자였다(Phase 2 나눔 작성 화면 진입점 예약). 나눔은 백엔드·공동체가 선행돼야 하는데, 복사는 지금 당장 쓰인다 — 고른 구절을 카톡에 붙여넣는 것이 실제 사용 맥락.
- 결과: 성공. `CopyVerseButton`으로 교체하고 자리 표시자는 삭제(사용자 결정 — "다음에 필요하면 다시 만드는 게 낫다"). Phase 2 진입점은 그때 새로 만든다.

**✅ D-702. 선택 스토어가 절 본문까지 보관 (`Set<VerseId>` → `Map<VerseId, {text, endVerseNum}>`)**
- 왜: 복사 텍스트를 만들려면 본문이 필요한데 `VerseId`는 권·장·절만 담는다. 버튼이 장 데이터를 다시 뒤지는 방법도 있으나, **피드는 위아래로 이어 붙고 떨어지므로 "선택한 절이 아직 마운트돼 있다"는 보장이 없다.** 고를 때 본문을 같이 담아두면 그 문제가 사라진다.
- 결과: 성공. D-102의 외부 스토어 구조(스냅샷 캐싱)는 그대로 — 스냅샷이 `VerseId[]`에서 객체 배열로 바뀌었을 뿐이라 절 행의 리렌더 비용은 여전히 O(1).

**✅ D-703. 연속한 절은 한 덩어리, 끊기면 새 덩어리**
- 왜: 고전 13:10,11,13을 고르면 `13:10-11` 한 문단과 `13:13` 한 문단이 나와야 읽힌다. 절마다 머리말을 붙이면 붙여넣은 쪽이 번호 잡음에 파묻힌다.
- 결과: 성공(`copy-text.ts`). 규칙 두 가지가 비자명하다.
  - 합본 절(신 6:18-19, D-203)의 다음은 20절이다. 이어짐 판정은 `verseNum`이 아니라 **`endVerseNum ?? verseNum`** 기준.
  - 장이 달라지면 번호가 이어져도(13:31 → 14:1) 덩어리를 나눈다. `[권 장:범위]` 머리말 한 줄에 담기지 않는 표기다.

**✅ D-704. 클립보드는 `navigator.clipboard` + `execCommand` 폴백**
- 왜: `navigator.clipboard`는 **보안 컨텍스트(HTTPS·localhost)에만 존재한다.** 이 앱의 실제 검증 경로는 폰에서 `http://192.168.x.x:3000`인데(D-405와 같은 제약), 거기서는 `undefined`라 조용히 죽는다.
- 결과: 성공(`lib/clipboard.ts`). 예외 없이 `boolean`을 돌려주고 실패는 버튼 라벨("복사하지 못했어요")로 드러낸다. 주의: 클립보드 호출 **앞에 `await`를 끼우면 안 된다** — iOS Safari가 사용자 제스처와의 연결을 끊고 두 경로 모두 거부한다.

**⚠️ D-705(수정). 복사 결과 표시를 이펙트가 아니라 파생 상태로**
- 실패: 처음엔 "선택이 바뀌면 이펙트로 상태를 idle로 되돌리기"였고, `react-hooks/set-state-in-effect`가 막았다(연쇄 렌더).
- 수정: 결과와 함께 **그때의 스토어 스냅샷 참조**를 들고 있다가 현재 스냅샷과 비교한다. 스냅샷은 선택이 바뀔 때만 새로 만들어지므로 참조가 곧 "그 선택"의 신분증이고, 표시가 저절로 만료된다. 교훈: "상태를 되돌리는 이펙트"는 대개 비교할 키를 안 들고 있다는 신호다.

### 영역 9 — 기도 (중보기도실)

**✅ D-901. 기도 카운트는 어제 기준을 유지한다** (사용자 결정)
- 왜: "**어제의 기도로 오늘을 산다**"는 것이 이 문구의 의미다. 오늘 기준으로 바꾸면 숫자가
  실시간으로 늘어 재방문 유인은 커지지만, 아침마다 0에서 시작해 그 의미가 사라진다.
  ERD의 기존 설계(D-303)와도 일치한다.
- 결과: 확정. `prayer_logs`에서 `prayed_on = 어제`로 집계. 오늘자 실시간 카운트는 노출하지 않는다.

**✅ D-902. 기도한 사람은 익명이다 — 수만 보여준다** (사용자 결정)
- 왜: 실명("김현정, 이수진이 기도했어요")이 훨씬 따뜻하지만, 동시에 "나는 저 사람을 위해
  기도 안 했는데"라는 부채감을 만든다. 그 부채감이 선순환의 연료가 될지 앱을 안 열게 만들지
  알 수 없고, 중보기도의 취지는 세어 갚는 관계가 아니다.
- 결과: 확정. `pray_by`는 저장하되(집중 모드의 "이미 기도한 사람 건너뛰기"에 필요) 화면에
  이름을 노출하지 않는다.

**✅ D-903. 기도제목이 없는 사람도 카드를 만든다 + 그것을 작성 유도에 쓴다** (사용자 아이디어)
- 왜: 기도제목이 없다고 목록에서 빠지면 조용한 사람이 기도에서 배제된다. 정작 그 사람이 가장
  필요할 수 있다. 더 중요한 건 그 다음이다 — **기도를 받은 직후가 마음이 가장 열리는 순간**이라,
  그때 "구체적인 필요를 나눠 주시겠어요?"를 성경 구절과 함께 건네면 첫 기도제목을 쓰게 만드는
  가장 좋은 타이밍이 된다. 초기 사용자의 빈 상태를 푸는 열쇠다.
- 결과: 확정. 카드에는 "아직 기도제목이 없어요"를 두고 기도는 누를 수 있게 한다.
- 주의: **이 유도를 푸시 알림에 걸면 MVP에서 동작하지 않는다.** 알림 도메인·PWA 푸시가 아직
  없다. 앱을 열었을 때 **메인 최상단**에서 같은 말을 하고, 푸시가 붙으면 같은 문구를 밖으로
  내보낸다. 구절은 이미 있는 개역개정 데이터에서 뽑는다(홈의 '오늘의 말씀'과 같은 방식).

**✅ D-904. 기도제목은 대문이 아니라 중보기도실에 모은다** (사용자 결정)
- 왜: 매일 반복하는 행위라 단계가 하나만 늘어도 안 하게 된다. 기존 시안은 중보기도실 →
  공동체 선택 → 목록으로 두 단계였다. 그리고 `prayer_logs`에는 **`community_id`가 없다** —
  기도는 애초에 방 단위가 아니라 사람 단위로 설계돼 있으므로, 사람 카드를 평평하게 늘어놓는
  화면이 데이터 모델과 정직하게 대응한다.
- 결과: 확정. 중보기도실 = "내가 볼 수 있는 모든 사람 + 각자의 최신 기도제목" 카드 목록.
  대문에는 '이주의 기도짝'만 남는다.

**✅ D-905. 여러 공동체에 걸친 사람은 하나로 합친다** (사용자 결정)
- 왜: 기도의 단위가 사람이므로, A방과 B방에 모두 있는 사람이 카드 두 장으로 나오면 안 된다.
- 결과: 확정. 다만 **목록의 범위와 정렬은 미확정**(아래 참조).

**✅ D-906. 익명 기도제목(`visibility='anonymous'`)은 MVP에서 뺀다** (사용자 결정)
- 왜: 이름이 붙으면 익명이 아니고, 이름이 없으면 "기도했어요"의 카운트를 누구에게 보낼지가
  성립하지 않는다. 즉 카드 목록에 섞일 수 없고 별도 구역이 되어야 하는데, 초기에 그 구조를
  하나 더 만들 값어치가 없다.

### 영역 10 — 공동체와 초대

**✅ D-1001. 공동체 목록 화면은 개수와 무관하게 항상 거친다** (사용자 결정 — 제안 반려)
- 왜 반려됐나: 제안은 "1개면 목록을 건너뛰고 바로 대문"이었고, 근거로 `/bible`이 이어읽던
  장으로 리다이렉트하는 선례를 들었다. **그 유비가 틀렸다.** `/bible`은 언제나 "읽던 장 하나"로
  가는 단일 개념이라 N개인 경우가 없다. 공동체는 개수가 1→2가 되는 순간 **탭을 눌렀을 때
  도착하는 곳이 말없이 바뀐다.** "공동체 탭 = 우리 방"으로 익힌 사용자에게서 익숙해진 것을
  빼앗는 변화다.
- 결과: 확정. 리다이렉트 없이 항상 목록.

**✅ D-1002. 목록의 각 줄은 이름 + 인원 수만** (사용자 결정)
- 왜: "새 나눔 3건" 같은 지표는 데이터가 쌓인 뒤에야 의미가 생긴다. 지금 붙이면 전부 0이다.
- 결과: 확정. 배지를 얹을 자리는 남겨 둔다.

**✅ D-1003. MVP 대문 = 이주의 기도짝 + 나눔 자료실 + 멤버 목록** (사용자 결정)
- 왜: 시안(`Community Page.png`)은 네 구역인데 **공지사항과 갤러리는 ERD에 테이블이 없다.**
  특히 갤러리는 오브젝트 스토리지라는 인프라 층이 새로 필요해, 핵심 루프에서 가장 먼 기능에
  먼저 끌려간다. 반면 나눔 자료실은 `sharings`·`sharing_communities`로 이미 받쳐진다.
- 결과: 확정. 기도짝(누구인지 + 그 사람 기도제목으로 바로 라우팅) · 나눔 자료실 · 그 아래
  멤버 목록. 멤버 목록 옆에 `+`(초대)와 `...`(관리) 버튼을 둔다. 공지사항·갤러리는 제외.

**✅ D-1004. 가입은 초대 링크 기반. 공개 검색은 배제** (사용자 결정)
- 왜: **기도제목은 이 앱에서 가장 사적인 데이터다.** 병·가정 문제·실직이 올라온다. 검색으로
  발견되는 방은 "모르는 사람이 들어와 읽을 수 있다"는 뜻이고, 그러면 사람들이 진짜 기도제목을
  쓰지 않는다. 그 순간 앱의 존재 이유가 사라진다. 게다가 교회 소그룹은 이미 오프라인에서
  관계가 정해진 집단이라 발견될 필요가 없다. 공동체 모델도 "카톡 단톡방처럼"이다(D-302).
- 결과: 확정. `/invite/{code}` 형태로 **링크가 곧 코드**다. 코드 직접 입력은 보조 수단.

**✅ D-1005. 로그인 후 초대 복귀는 `pending_invite` 쿠키로**
- 왜: `/invite/{code}`는 Next 페이지라 Spring의 `HttpSessionRequestCache`가 모른다. 초대
  페이지를 **로그인 없이 열어** 방 이름을 먼저 보여주고(어디 들어가는지 모른 채 로그인을
  요구하면 이탈한다), 로그인 버튼에서 코드를 쿠키에 심은 뒤 OAuth로 보낸다.
- 결과: 확정. 쿠키에는 **경로가 아니라 코드만** 담는다 — 경로를 담고 그리로 리다이렉트하면
  오픈 리다이렉트가 열린다. 이어읽기 쿠키(D-103)와 같은 신뢰 경계 규칙.
- 가입은 복귀 후 **버튼을 한 번 더** 누르게 한다. 자동 가입은 잘못 누른 링크를 되돌릴 수 없다.

**⚠️ D-1006. 카카오톡 인앱 브라우저가 Google OAuth를 차단한다**
- 왜 문제인가: 초대 링크의 주 유통 경로가 카톡인데, 카톡에서 링크를 누르면 인앱 브라우저가
  열리고 **Google이 임베디드 웹뷰에서의 OAuth를 거부한다**(`disallowed_useragent`). 즉 지금
  설계대로면 **주 유입 경로에서 로그인이 아예 안 된다.**
- 결과: 미확정. 대응은 (a) 카카오 로그인 추가 — `user_identities`에 `provider='kakao'`가 이미
  있어 스키마 변경은 없다, (b) 외부 브라우저로 열도록 안내 — 안드로이드는 `intent://`로 강제
  가능하나 iOS는 안내만 가능해 이탈이 생긴다, (c) 둘 다.
- 로드맵의 "Kakao/Naver는 후속"은 이 사실을 모르고 쓴 것이다. **첫 사용자가 누구냐(D-802)에
  따라 카카오 로그인이 후속이 아니라 필수 조건이 된다.**

---

### 이 세션에서 **미확정**으로 남은 것

착수 전에 정해야 하는 순서대로.

1. **첫 공동체를 누구로 시작할 것인가** (D-802) — 이게 아래 2번을 좌우한다.
2. **카카오 로그인을 MVP에 넣을 것인가** (D-1006).
3. **중보기도실 목록의 범위와 정렬.** 사람 단위 합침만 확정됐다(D-905). 여러 방에 속하면
   카드가 수십 장이 되는데, 이름순으로 두면 앞사람만 기도받아 "모두가 공평히 기도받는다"는
   D-303의 취지가 무너진다. 제안은 **오늘 내가 아직 기도 안 한 사람 먼저, 그 안에서 최근에
   적게 받은 사람 먼저** — 둘 다 `prayer_logs`로 계산되고, 이 정렬을 한 명씩 보여주는 것이
   곧 집중 모드다(즉 집중 모드는 별개 기능이 아니다).
4. **카운트가 0일 때의 문구.** 어제 기준이라(D-901) **가입 첫날은 반드시 0**이고 조용한 날도
   0이다. "오늘도 0명의 기도로 살고 있어요"는 따뜻하지 않고 상처가 된다. 매일 보는 화면의
   기본 상태라 이 문구가 기능의 성패를 가른다.
5. **기도제목의 수명.** "최신 하나만"이라(D-304) 3개월 전 제목이 계속 최신으로 남아 이미
   응답된 기도를 붙들게 된다. 만료까지 만들 필요는 없고, 카드에 "○일 전"만 붙여도 오래된
   제목이 스스로 드러난다.
6. **초대 코드의 만료·재발급·리더 승인.** 코드가 곧 입장 권한인데 단톡방에 뿌린 링크는 어디로든
   퍼진다. MVP는 재발급만으로 버틸 수 있으나, 기도제목의 민감도를 생각하면 리더 승인이 생각보다
   일찍 필요해질 수 있다. 코드는 추측 불가능하도록 10~12자 랜덤으로.
