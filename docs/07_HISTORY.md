### 영역 1 — 성경 리더

**✅ D-101. 상단 헤더를 sticky로 두고 장 제목 밴드를 z-index로 덮는다**
- 왜: 헤더와 밴드가 둘 다 sticky면 밴드의 `top`을 헤더 표시 여부에 따라 토글해야 해서 모든 장 섹션에 스크롤 클래스가 붙는다. 헤더(z-30)가 밴드(z-20)를 덮으면 밴드는 `top-0`에 그대로 두면 된다(사용자 제안).
- 결과: 성공. 밴드가 헤더 밑으로 미끄러져 들어가고 배경(`bg-header`)이 같아 이어지듯 보인다.

**✅ D-102. 헤더의 장 숫자를 useState가 아니라 외부 스토어로 관리**
- 왜: 공통 조상에 useState로 두면 장이 바뀔 때마다 `ChapterFeed`가 리렌더되어 **이어 붙인 모든 절**이 다시 그려진다. `useSyncExternalStore`로 헤더만 숫자를 구독하면 O(1).
- 결과: 성공. `CurrentChapterProvider` 신설.

**✅ D-103. 이어읽기를 localStorage가 아니라 쿠키로**
- 왜: 서버에서 읽어야 `/bible`이 서버 리다이렉트로 이어읽고, `BottomNav`가 서버 컴포넌트로 남는다. 쿠키 값은 조작 가능한 입력이라 `getBook` + 장 범위로 검증(오픈 리다이렉트 방지).
- 결과: 성공. 조작 쿠키 14종 차단 확인.

**✅ D-104. 이전 장은 진입 시 DOM에 붙이고 위치를 한 번만 잡는다** (사용자 지시로 재설계)
- 왜: 처음엔 "스크롤이 이전 장을 부르고 → 붙으면 보정" 순서라 보정이 iOS 관성과 싸워 `/ps/43`이 41·42로 밀렸다. "직전 장은 DOM으로 불러오되 보이는 위치만 조정하라"는 지시로, 진입 시 스크롤 무관하게 한 장 붙이고 다 붙은 문서에서 위치를 한 번 잡게 바꿈.
- 결과: 성공. 주소=헤더=화면이 어떤 스크롤에도 일치.

**✅ D-105. 현재 장 판정 띠를 헤더 높이만큼 내린다**
- 왜: 판정 띠가 `상단 10%`(62.9px)였는데 헤더가 63px이라 **헤더에 완전히 가린 영역**을 보고 판정 → 화면엔 42편인데 헤더·주소는 41편. 원래 주석 "고정된 밴드와 같은 지점"은 헤더가 숨던 시절 전제였고, 헤더가 항상 뜨게 되며 깨졌다.
- 결과: 성공.

**❌ D-106(폐기). 이전 장 센티넬 마진을 다음 장과 대칭(600px)으로 두기**
- 왜 시도: 다음 장 프리페치와 대칭이 자연스러워 보였다.
- 실패 이유: 진입 즉시 이전 장을 당기고, 시편처럼 장이 짧으면 연쇄로 당기며 매번 스크롤 보정이 필요했다. iOS 관성 중 프로그램적 스크롤이 무시되면 밀렸다. → D-104로 대체.

**⚠️ D-107. `next start`/헤드리스로만 검증한 것의 한계**
- 초기 리더 이슈들을 Chromium 헤드리스로만 검증했는데, iOS 모멘텀·Safari 고유 동작(scroll anchoring 없음)은 재현이 안 됐다. 실기기(WebKit/실 Safari) 확인이 최종 기준임을 반복 학습.

### 영역 2 — 성경 데이터 소스 (실패한 소스들 분리)

**❌ D-201(폐기). 개역한글 `thiagobodruk/ko_ko.json`**
- 왜 시도: 원래 앱에 들어 있던 소스.

**❌ D-202(폐기). getbible 개역성경**
- 왜 시도: 개역한글 대체 후보. 장은 온전했다.
- 실패 이유: 사본 생략절(막 9:44 등)을 **지우고 번호를 당겨** 같은 종류의 오류를 새로 만들었다. `?`·`!`·인용부호도 전무.

**✅ D-203. 개역개정 `bible.json` 채택 (번역본 교체)**
- 왜: 66권/1189장 완전, 빈 장 0, 생략절 13곳을 `(없음)`으로 정확히 표기, 행 24:7 부재도 정본과 일치. `elroi773/bible-api`는 188절짜리 랜덤 구절 API라 후보 탈락.
- 결과: 성공. 번역본이 개역한글→개역개정으로 바뀜(사용자 승인).
- 부수: `요18:이` 파싱 사고(절 번호 자리에 본문 “이”가 들어감) 1건 복원. 합본 절 11곳(신 6:18-19 등)에 `endVerseNum` 도입.

**✅ D-204. NUL 패딩 제거를 빌드에서 강제**
- 왜: 원본이 3개 절(삿 21:25, 습 3:20, 벧전 5:14, 각 권 마지막 절)을 NUL로 패딩. 화면엔 안 보이지만 **Postgres text 타입이 NUL을 못 담아** 시드 적재가 통째로 실패. `\s`가 NUL을 안 걸러 `trim()`도 못 지운다.
- 결과: 성공. `normalize()`가 제어문자를 걷어내고, 남으면 빌드가 멈추는 가드 추가. **실제 Postgres에 부어보다 발견** — 생성만 하고 넘어갔으면 놓쳤을 것.

### 영역 3 — ERD / 스키마

**✅ D-301. 전체 도메인 ERD를 먼저 설계 (build-first 아님)**
- 왜: 메인 화면 하나가 기도·공동체·성경을 동시에 참조하고, 나눔이 여러 공동체에 크로스포스트되는 등 도메인이 얽혀 있어, 관계를 먼저 못 박지 않으면 나중에 테이블을 다시 잡게 된다.
- 결과: 성공. 임시 Postgres에 부어 시나리오 + 나쁜 데이터 13종 차단 검증.

**✅ D-302. 공동체는 계층 없이 평평** (사용자 결정)
- 왜: 카톡 단톡방처럼 생성 시 이름 짓고 모임장이 수정. 교회-지부-반 트리는 확정 요구가 아니라 `parent_id` 없이 이름 문자열로만.

**✅ D-303. 기도 카운트는 사람 기준 + 하루 하나** (사용자가 설계 중 수정)
- 왜: 처음엔 `prayer_logs`를 기도제목(sharing) 기준으로 잡았으나, 기도 상세의 "기도했어요" 버튼이 **사람 카드**에 하나 붙어 있음 → 제목 기준(좋아요식)은 인기 제목에 몰려 중보기도 취지에 어긋남. 키를 `(기도받는 사람, 기도한 사람, 날짜)`로 바꿈. sharing_id 미포함.
- 결과: 성공. 로그 테이블을 두는 이유 = "카운트만"으론 하루 집계도 집중모드 건너뛰기도 불가.

**✅ D-304. 기도제목 = prayer 타입 나눔, 최신만 노출**
- 별도 prayers 테이블 없음(작성 화면이 나눔과 동일). `ORDER BY created_at DESC LIMIT 1`로 최신만.

**✅ D-305. PK는 SERIAL 유지** (사용자 결정) — 기존 성경 3테이블과 일관.

### 영역 4 — 인증 (Google OAuth)

**✅ D-401. Next 프록시 + Spring 세션 (JWT 아님)** (사용자 결정)
- 왜: 브라우저가 :3000만 상대하고 Spring(:8080)은 프록시 뒤 → 세션 쿠키가 first-party라 dev(http)에서 CORS·SameSite 문제 없음. `forward-headers-strategy=framework`로 프록시 뒤에서도 redirect_uri가 :3000으로 생성됨(검증).
- 결과: 성공. `/api/v1/me` 401, `/oauth2/authorization/google` 302(accounts.google.com)까지 검증.

**✅ D-402. Spring Boot 4 / Security 7 API를 문서·JAR로 확인하며 작성**
- 왜: 학습 범위(Boot 3 / Security 6) 밖. 메모리로 쓰면 위험.
- 결과: 성공(compileJava 통과). `spring-boot-starter-oauth2-client`가 의존성에서 **빠져 있어** 추가. `ddl-auto=validate`로 init-db.sql 스키마와 엔티티 일치 검증.

**✅ D-403. `/api/v1/me`를 rewrite가 아니라 Next 라우트 핸들러로**
- 왜: rewrite 프록시는 백엔드가 꺼져 있으면 매 요청 `ECONNREFUSED`를 로그에 도배(프론트만 개발할 때 흔함). 라우트 핸들러는 백엔드 다운 시 조용히 401.
- 결과: 성공. OAuth 경로(브라우저 리다이렉트)는 rewrite 유지.

**⚠️ D-404. CSRF 임시 비활성 (MVP)**
- 왜: 변경 API가 로그인/로그아웃뿐이라 위험이 낮고 로그아웃 POST를 단순화. `SecurityConfig`에 TODO.
- 주의: **v1.1 나눔·기도 쓰기 전 반드시 재활성.** 세션 쿠키 앱은 CSRF에 취약.

**⚠️ D-405. Google OAuth는 dev에서 localhost만.** 사설 IP(192.168.x.x)·비HTTPS 거부 → 폰(LAN IP)으로 로그인 불가, HTTPS(배포/터널) 필요. 실제 Google 로그인 end-to-end는 사용자만 검증 가능(헤드리스 불가).

### 영역 6 — Vercel 배포 (실패가 가장 많았던 구간, 분리 서술)

최종 원인은 하나였다: **Vercel 프로젝트의 `framework` 설정이 `null`** 이라 Vercel이 `@vercel/next`가 아니라 `@vercel/static-build`로 빌드 → `next build`는 돌지만 `.next`가 Next 앱으로 처리되지 않고 public 자산만 복사 + "모든 경로 404" 라우팅 생성 → 전 라우트 `x-vercel-error: NOT_FOUND`.

#### ❌ 실패한 시도들 (각각 왜 무효였나)

**❌ D-601. push하면 Vercel이 알아서 앱을 찾겠지**
- 실패 이유: 모노레포. Next 앱이 `apps/frontend/`에 있고 저장소 루트엔 `package.json`이 없어 프레임워크 미감지 → 404.

**⚠️ D-602. Root Directory = `apps/frontend` 설정**
- 필요조건이나 불충분. 빌드는 `apps/frontend`에서 돌게 됐지만, 초기 미감지로 잡힌 **`framework: null`이 그대로 남아** 여전히 정적 빌더 사용 → 404 지속.

**❌ D-603. Deployment Protection이 원인이라는 가설**
- 왜 시도: 배포 URL을 fetch하니 `vercel.com/sso-api`로 302 리다이렉트 → 인증 벽 확인.
- 실패 이유: 벽을 껐는데도 404. 그리고 사용자(계정 주인)가 데스크톱에서도 404. Protection은 **A 블로커였지 THE 404 원인이 아니었다.** 옛 프로젝트(빈 빌드)와 새 프로젝트(기본 Protection 켜짐)가 겹쳐 진단을 흐림. "Protection이면 전에도 됐어야지"라는 사용자 지적이 정확했음.

**❌ D-604. 대시보드에서 Framework Preset을 Next.js로**
- 실패 이유: 사용자가 설정했다는데 `vercel pull`로 확인하니 여전히 `framework: null`. 대시보드 설정이 이 케이스에선 저장/반영 안 됨.

**❌ D-605. `next build --webpack` (Turbopack이 원인이라는 가설)**
- 왜 시도: 빌드 로그의 `(Turbopack)`이 유일한 비표준 요소로 보여, Vercel이 Turbopack 프로덕션 출력을 서빙 못 한다고 추정.
- 실패 이유: 완전 헛다리. 실제 빌더가 `@vercel/static-build`였으니 Turbopack이든 webpack이든 무관. **불필요한 변경**(무해하지만).

**❌ D-606. 잘못된 URL 테스트**
- 실패 이유: 옛 프로젝트의 배포 해시 URL(`manna-7quu08tkq-…`)을 찍어 404를 봤는데, 그건 죽은 옛 배포였다. 진짜 프로덕션 별칭(`manna-five-tau`)이 따로 있었다.

#### ✅ 유효했던 결정적 실험/수정

**✅ D-607. 로컬 프로덕션 재현 (`next build && next start`)**
- 왜: 코드/빌드 vs Vercel 서빙을 가르는 실험.
- 결과: 로컬 프로덕션 서버에서 `/`·`/login`·`/landing` 전부 200 → **코드/빌드는 정상, Vercel 서빙이 문제**로 확정. 이걸 처음부터 했으면 D-603·D-605 헛다리를 안 짚었을 것.

**✅ D-608. `vercel build` 로컬 재현 + `.vercel/output` 해부**
- 왜: Vercel의 변환을 로컬에서 재현해 라우팅 config를 눈으로 확인.
- 결과: **근본 원인 발견.** `config.json`이 "모든 걸 404"만 담고 `functions/` 없음. diagnostics의 `builder.name: "@vercel/static-build"`, `framework: null`이 결정적 증거.

**✅ D-609. `apps/frontend/vercel.json`에 `framework: "nextjs"` 명시**
- 왜: 프로젝트 설정의 null을 **코드로 오버라이드**. 대시보드 설정이 안 먹었으니(D-604) 버전 관리되는 vercel.json이 더 확실.
- 결과: 성공. `vercel build` 재현 시 `@vercel/next` 사용 → config.json 라우트 35개 + `functions/` 생성. push 후 git 배포(57초, Ready, Production)가 정상 200.

#### 메타 교훈 (이 세션)
- **추측→재배포 루프가 최악.** 재배포는 피드백이 느리고 변수가 많다.
- **로컬 재현을 먼저.** `next start`(코드/빌드 확인) → `vercel build`(플랫폼 변환 확인)가 원격을 찌르기 전에 왔어야 했다.
- **증상(404)은 여러 원인을 가린다.** Protection·Turbopack·URL 혼동이 다 겹쳤다. 헤더(`x-vercel-error`)와 빌더 diagnostics 같은 **기계적 증거**로 갈라야 한다.

### 영역 7 — 구절 복사

**✅ D-701. 절 선택 후 동작을 '나눔하기'가 아니라 '복사하기'로** (사용자 결정)
- 왜: `ShareVerseButton`은 `onClick`이 없는 자리 표시자였다(Phase 2 나눔 작성 화면 진입점 예약). 나눔은 백엔드·공동체가 선행돼야 하는데, 복사는 지금 당장 쓰인다 — 고른 구절을 카톡에 붙여넣는 것이 실제 사용 맥락.
- 결과: 성공. `CopyVerseButton`으로 교체하고 자리 표시자는 삭제(사용자 결정 — "다음에 필요하면 다시 만드는 게 낫다"). Phase 2 진입점은 그때 새로 만든다.

**✅ D-702. 선택 스토어가 절 본문까지 보관 (`Set<VerseId>` → `Map<VerseId, {text, endVerseNum}>`)**
- 왜: 복사 텍스트를 만들려면 본문이 필요한데 `VerseId`는 권·장·절만 담는다. 버튼이 장 데이터를 다시 뒤지는 방법도 있으나, **피드는 위아래로 이어 붙고 떨어지므로 "선택한 절이 아직 마운트돼 있다"는 보장이 없다.** 고를 때 본문을 같이 담아두면 그 문제가 사라진다.
- 결과: 성공. D-102의 외부 스토어 구조(스냅샷 캐싱)는 그대로 — 스냅샷이 `VerseId[]`에서 객체 배열로 바뀌었을 뿐이라 절 행의 리렌더 비용은 여전히 O(1).

**✅ D-703. 연속한 절은 한 덩어리, 끊기면 새 덩어리**
- 왜: 고전 13:10,11,13을 고르면 `13:10-11` 한 문단과 `13:13` 한 문단이 나와야 읽힌다. 절마다 머리말을 붙이면 붙여넣은 쪽이 번호 잡음에 파묻힌다.
- 결과: 성공(`copy-text.ts`). 규칙 두 가지가 비자명하다.
  - 합본 절(신 6:18-19, D-203)의 다음은 20절이다. 이어짐 판정은 `verseNum`이 아니라 **`endVerseNum ?? verseNum`** 기준.
  - 장이 달라지면 번호가 이어져도(13:31 → 14:1) 덩어리를 나눈다. `[권 장:범위]` 머리말 한 줄에 담기지 않는 표기다.

**✅ D-704. 클립보드는 `navigator.clipboard` + `execCommand` 폴백**
- 왜: `navigator.clipboard`는 **보안 컨텍스트(HTTPS·localhost)에만 존재한다.** 이 앱의 실제 검증 경로는 폰에서 `http://192.168.x.x:3000`인데(D-405와 같은 제약), 거기서는 `undefined`라 조용히 죽는다.
- 결과: 성공(`lib/clipboard.ts`). 예외 없이 `boolean`을 돌려주고 실패는 버튼 라벨("복사하지 못했어요")로 드러낸다. 주의: 클립보드 호출 **앞에 `await`를 끼우면 안 된다** — iOS Safari가 사용자 제스처와의 연결을 끊고 두 경로 모두 거부한다.

**⚠️ D-705(수정). 복사 결과 표시를 이펙트가 아니라 파생 상태로**
- 실패: 처음엔 "선택이 바뀌면 이펙트로 상태를 idle로 되돌리기"였고, `react-hooks/set-state-in-effect`가 막았다(연쇄 렌더).
- 수정: 결과와 함께 **그때의 스토어 스냅샷 참조**를 들고 있다가 현재 스냅샷과 비교한다. 스냅샷은 선택이 바뀔 때만 새로 만들어지므로 참조가 곧 "그 선택"의 신분증이고, 표시가 저절로 만료된다. 교훈: "상태를 되돌리는 이펙트"는 대개 비교할 키를 안 들고 있다는 신호다.

### 영역 9 — 기도 (중보기도실)

**✅ D-901. 기도 카운트는 어제 기준을 유지한다** (사용자 결정)
- 왜: "**어제의 기도로 오늘을 산다**"는 것이 이 문구의 의미다. 오늘 기준으로 바꾸면 숫자가
  실시간으로 늘어 재방문 유인은 커지지만, 아침마다 0에서 시작해 그 의미가 사라진다.
  ERD의 기존 설계(D-303)와도 일치한다.
- 결과: 확정. `prayer_logs`에서 `prayed_on = 어제`로 집계. 오늘자 실시간 카운트는 노출하지 않는다.

**✅ D-902. 기도한 사람은 익명이다 — 수만 보여준다** (사용자 결정)
- 왜: 실명("김현정, 이수진이 기도했어요")이 훨씬 따뜻하지만, 동시에 "나는 저 사람을 위해
  기도 안 했는데"라는 부채감을 만든다. 그 부채감이 선순환의 연료가 될지 앱을 안 열게 만들지
  알 수 없고, 중보기도의 취지는 세어 갚는 관계가 아니다.
- 결과: 확정. `pray_by`는 저장하되(집중 모드의 "이미 기도한 사람 건너뛰기"에 필요) 화면에
  이름을 노출하지 않는다.

**✅ D-903. 기도제목이 없는 사람도 카드를 만든다 + 그것을 작성 유도에 쓴다** (사용자 아이디어)
- 왜: 기도제목이 없다고 목록에서 빠지면 조용한 사람이 기도에서 배제된다. 정작 그 사람이 가장
  필요할 수 있다. 더 중요한 건 그 다음이다 — **기도를 받은 직후가 마음이 가장 열리는 순간**이라,
  그때 "구체적인 필요를 나눠 주시겠어요?"를 성경 구절과 함께 건네면 첫 기도제목을 쓰게 만드는
  가장 좋은 타이밍이 된다. 초기 사용자의 빈 상태를 푸는 열쇠다.
- 결과: 확정. 카드에는 "아직 기도제목이 없어요"를 두고 기도는 누를 수 있게 한다.
- 주의: **이 유도를 푸시 알림에 걸면 MVP에서 동작하지 않는다.** 알림 도메인·PWA 푸시가 아직
  없다. 앱을 열었을 때 **메인 최상단**에서 같은 말을 하고, 푸시가 붙으면 같은 문구를 밖으로
  내보낸다. 구절은 이미 있는 개역개정 데이터에서 뽑는다(홈의 '오늘의 말씀'과 같은 방식).

**✅ D-904. 기도제목은 대문이 아니라 중보기도실에 모은다** (사용자 결정)
- 왜: 매일 반복하는 행위라 단계가 하나만 늘어도 안 하게 된다. 기존 시안은 중보기도실 →
  공동체 선택 → 목록으로 두 단계였다. 그리고 `prayer_logs`에는 **`community_id`가 없다** —
  기도는 애초에 방 단위가 아니라 사람 단위로 설계돼 있으므로, 사람 카드를 평평하게 늘어놓는
  화면이 데이터 모델과 정직하게 대응한다.
- 결과: 확정. 중보기도실 = "내가 볼 수 있는 모든 사람 + 각자의 최신 기도제목" 카드 목록.
  대문에는 '이주의 기도짝'만 남는다.

**✅ D-905. 여러 공동체에 걸친 사람은 하나로 합친다** (사용자 결정)
- 왜: 기도의 단위가 사람이므로, A방과 B방에 모두 있는 사람이 카드 두 장으로 나오면 안 된다.
- 결과: 확정. 다만 **목록의 범위와 정렬은 미확정**(아래 참조).

**✅ D-906. 익명 기도제목(`visibility='anonymous'`)은 MVP에서 뺀다** (사용자 결정)
- 왜: 이름이 붙으면 익명이 아니고, 이름이 없으면 "기도했어요"의 카운트를 누구에게 보낼지가
  성립하지 않는다. 즉 카드 목록에 섞일 수 없고 별도 구역이 되어야 하는데, 초기에 그 구조를

### 영역 10 — 공동체와 초대

**✅ D-1001. 공동체 목록 화면은 개수와 무관하게 항상 거친다** (사용자 결정 — 제안 반려)
- 왜 반려됐나: 제안은 "1개면 목록을 건너뛰고 바로 대문"이었고, 근거로 `/bible`이 이어읽던
  장으로 리다이렉트하는 선례를 들었다. **그 유비가 틀렸다.** `/bible`은 언제나 "읽던 장 하나"로
  가는 단일 개념이라 N개인 경우가 없다. 공동체는 개수가 1→2가 되는 순간 **탭을 눌렀을 때
  도착하는 곳이 말없이 바뀐다.** "공동체 탭 = 우리 방"으로 익힌 사용자에게서 익숙해진 것을
  빼앗는 변화다.
- 결과: 확정. 리다이렉트 없이 항상 목록.

**✅ D-1002. 목록의 각 줄은 이름 + 인원 수만** (사용자 결정)
- 왜: "새 나눔 3건" 같은 지표는 데이터가 쌓인 뒤에야 의미가 생긴다. 지금 붙이면 전부 0이다.
- 결과: 확정. 배지를 얹을 자리는 남겨 둔다.

**✅ D-1003. MVP 대문 = 이주의 기도짝 + 나눔 자료실 + 멤버 목록** (사용자 결정)
- 왜: 시안(`Community Page.png`)은 네 구역인데 **공지사항과 갤러리는 ERD에 테이블이 없다.**
  특히 갤러리는 오브젝트 스토리지라는 인프라 층이 새로 필요해, 핵심 루프에서 가장 먼 기능에
  먼저 끌려간다. 반면 나눔 자료실은 `sharings`·`sharing_communities`로 이미 받쳐진다.
- 결과: 확정. 기도짝(누구인지 + 그 사람 기도제목으로 바로 라우팅) · 나눔 자료실 · 그 아래
  멤버 목록. 멤버 목록 옆에 `+`(초대)와 `...`(관리) 버튼을 둔다. 공지사항·갤러리는 제외.

**✅ D-1004. 가입은 초대 링크 기반. 공개 검색은 배제** (사용자 결정)
- 왜: **기도제목은 이 앱에서 가장 사적인 데이터다.** 병·가정 문제·실직이 올라온다. 검색으로
  발견되는 방은 "모르는 사람이 들어와 읽을 수 있다"는 뜻이고, 그러면 사람들이 진짜 기도제목을
  쓰지 않는다. 그 순간 앱의 존재 이유가 사라진다. 게다가 교회 소그룹은 이미 오프라인에서
  관계가 정해진 집단이라 발견될 필요가 없다. 공동체 모델도 "카톡 단톡방처럼"이다(D-302).
- 결과: 확정. `/invite/{code}` 형태로 **링크가 곧 코드**다. 코드 직접 입력은 보조 수단.

**✅ D-1005. 로그인 후 초대 복귀는 `pending_invite` 쿠키로**
- 왜: `/invite/{code}`는 Next 페이지라 Spring의 `HttpSessionRequestCache`가 모른다. 초대
  페이지를 **로그인 없이 열어** 방 이름을 먼저 보여주고(어디 들어가는지 모른 채 로그인을
  요구하면 이탈한다), 로그인 버튼에서 코드를 쿠키에 심은 뒤 OAuth로 보낸다.
- 결과: 확정. 쿠키에는 **경로가 아니라 코드만** 담는다 — 경로를 담고 그리로 리다이렉트하면
  오픈 리다이렉트가 열린다. 이어읽기 쿠키(D-103)와 같은 신뢰 경계 규칙.
- 가입은 복귀 후 **버튼을 한 번 더** 누르게 한다. 자동 가입은 잘못 누른 링크를 되돌릴 수 없다.

**⚠️ D-1006. 카카오톡 인앱 브라우저가 Google OAuth를 차단한다**

**⚠️ D-1507. `useSyncExternalStore`의 getSnapshot이 매번 새 객체를 만들면 무한 루프**
- `jumpNav()`가 `{ back, forward }`를 그 자리에서 만들어 돌려주면 렌더가 멈추지 않는다.
- 수정: 자취가 바뀔 때만 다시 만들어 캐시하고(`nav`), **양쪽 다 없을 때는 고정 객체
  `NO_JUMP_NAV`** 를 돌려준다. 서버 스냅샷도 같은 객체다 — 없는 상태끼리는 정체성이
  흔들리지 않아야 한다.
- 교훈: 외부 스토어에서 **파생값**을 내보낼 때는 파생값도 스토어와 같이 캐시한다.

**✅ D-1508. 신뢰 경계는 `load()` 한 곳, 하나라도 이상하면 자취를 통째로 버린다**
- sessionStorage는 devtools로 얼마든지 고칠 수 있고, 이 값이 그대로 `router.push`의 경로가
  된다(오픈 리다이렉트).
- 쿠키와 같은 `"{abbrev}/{n}"` 형식으로 저장해서 `lastReadLocation`의 검증(실재하는 권인지,
  장이 범위 안인지)을 그대로 재사용한다.
- **일부만 걸러내지 않는다** — 하나를 빼면 `index`가 가리키던 자리가 의미를 잃는다.
  깨끗이 비우는 편이 안전하고 단순하다.
- 저장소 접근 거부(사파리 프라이빗 모드)와 깨진 JSON이 같은 `catch`로 온다. 어느 쪽이든
  "기록 없음"으로 시작하면 되고, 못 써도 이번 세션 동안은 메모리 캐시로 그대로 동작한다.

**✅ D-1509. 하단에 뜨는 것은 `ReaderChrome`이 전부 소유한다**
- 좌하단 이전 / 우하단 다음 / 가운데 복사·해제 / 아래 네비가 전부 같은 200ms로 함께 움직인다.
  `bottom-4`(16px) + `-translate-y-16`(64px) = 80px — 네비가 보일 때의 위치.
- **오프셋을 각자 하드코딩하면 반드시 겹친다.** 그래서 `navHidden`을 내려보내는 한 곳에서
  같이 렌더한다.
- 절을 고르는 중에는 양쪽 버튼이 숨는다. 좁은 화면에서 가운데 복사 버튼과 가로로 부딪히고,
  무엇보다 **고르는 중은 이동하는 중이 아니다.**

**✅ D-1510. 스크롤 위치는 복원하지 않는다**
- 무한 피드 한가운데로 되돌리는 건 방금 닫은 스크롤 튐(D-1101~1105)과 같은 지뢰밭이다.

**✅ D-1511. 생김새는 흰 배경 + 청록 테두리, 방향만 다르고 둘이 같다**

### 영역 16 — 404와 아직 없는 탭

**✅ D-1601. 404 화면을 먼저 만들고, 라우팅은 그 다음에** (사용자 결정)
- 순서를 뒤집으면 세 칸을 막는 동안 어디로 떨어지는지 볼 수가 없다. 받는 곳을 먼저 만들어
  놓으면 그 화면을 보면서 "여기로 떨어져도 되는가"를 판단할 수 있다.
- 실제로 그 판단이 D-1602를 갈랐다.

**✅ D-1602. 하단 네비 세 칸은 404가 아니라 "준비 중" 화면을 준다**
- 404를 그대로 두는 선택지도 있었다. 갈랐던 기준: **이 셋은 오타로 들어오는 자리가 아니라
  네비가 늘 가리키고 있어 눌러서 들어오는 자리다.** 없는 페이지가 아니라 아직 안 만든
  페이지이므로, 그렇게 말해 주는 편이 정직하다.
- 홈이 이미 "곧 제공" 섹션 스텁을 쓰고 있었다(`app/page.tsx`의 `ComingSoon`). 같은 말을
  화면 크기로 옮긴 것뿐이라 새 언어를 만들지 않았다.
- 상단바·하단 네비를 그대로 둔다 — 막다른 곳에 갇히면 안 되고, 눌러 본 탭이 눌린 채로
  남아 있어야 방금 어디를 눌렀는지 안다.

**✅ D-1603. 색은 홈의 도메인 배분을 그대로 따른다**
- `surface-warm`=공동체 · `surface-love`=기도 · `surface-cool`=나눔/말씀
  (globals.css의 시맨틱 토큰). 홈에서 "곧 제공"이라고 본 그 색이 여기서도 나오면 같은
  것으로 읽힌다.
- primitive를 직접 참조하지 않으려고 prop을 `"love" | "warm" | "cool"`로 받아 컴포넌트
  안에서 클래스로 바꾼다. 호출부가 Tailwind 클래스 문자열을 넘기면 그 파일이 토큰 체계를
  알아야 한다.

**✅ D-1604. 404의 두 번째 버튼은 성경으로 보낸다**
- 문구는 성경에 한정하지 않는다(주소 오타도 여기로 온다). 다만 **의도적으로 `notFound()`를
  부르는 유일한 자리가 리더**(없는 권 `/bible/zz/1`, 범위 밖 장 `/bible/gn/99`)라
  되돌려 보낼 곳이 분명하다.
- 큰 CTA는 로그인 화면의 리듬(`h-14` · `rounded-xl` · `text-base`)을 따른다. 상단바
  아이콘 버튼(`h-8`~`h-9`)과 섞이지 않도록 전면 화면의 주 동작은 이 크기로 통일한다.

**⚠️ D-1605. 셸 안에서는 화면 제목이 h1이 아니라 h2다**
- 처음엔 `ComingSoonScreen`의 제목을 h1으로 썼는데, `MainTopBar`가 이미 "Manna"를 h1으로
  갖고 있어 **한 페이지에 h1이 둘**이 됐다.
- 404는 상단바가 없어 거기서만 h1이 화면 제목으로 간다. 상단바를 쓰는 셸이면 h2다.
- 잡는 법: `curl` 후 `<h1`을 세는 것으로 충분했다. 타입체크·린트는 이걸 못 잡는다.

**📝 메모. 개발 모드에서 모든 페이지 HTML에 404 문구가 섞여 나온다**
- `/`나 `/community`를 받아 grep하면 "여기는 아직 빈 자리예요"가 걸린다. **버그가 아니다** —
  App Router가 not-found 바운더리를 RSC flight 페이로드에 같이 실어 보내는 것이고,
  이스케이프된 `<script>` 안이라 화면에는 안 나온다.
- 검증할 때 본문 grep이 아니라 `<h1>`/`<h2>` 같은 **실제 태그**를 봐야 하는 이유다.

**✅ D-1705. 카운트가 0이면 그 줄을 숨기고, 자리를 기도 유도로 바꾼다** (사용자 결정)
- 왜 숨기나: 어제 기준이라(D-901) **가입 첫날은 반드시 0**이고 조용한 날도 0이다.
  그런데 0은 틀린 숫자가 아니라 **"어제의 기도로 오늘을 산다"가 성립하지 않는 상태**다.
  게다가 이 앱을 쓰는 사람들의 기도만 세는 숫자라, 0이 "아무도 기도하지 않았다"를
  뜻하지도 않는다. 없는 문장을 0으로 우겨 넣으면 따뜻하지 않고 상처가 된다.
- **랜덤 문구는 반려.** 매일 여는 같은 자리에서 문구가 매번 바뀌면 "아무 말이나 하는
  자리"가 된다. 숫자가 뜰 때 그 자리가 사실을 말해서 쌓아 둔 신뢰가 깎인다.
- 대신 **그 자리를 행동으로 바꾼다.** D-903이 이미 메인 최상단을 작성 유도용으로 잡아
  두었으므로, 0인 날은 "오늘 ○○님을 위해 기도해 보세요" + 중보기도실 링크를 둔다.
- 왜 그게 맞나: 받은 것이 없을 때 **주는 쪽으로 방향을 돌리는 것**이 중보기도의 취지와
  맞고, 실제로 **0을 깨는 유일한 경로**다 — 내가 누르면 상대에게 앱을 열 이유가 생긴다.
- 결과: 확정.

**✅ D-1706. 기도제목은 append-only를 유지하고, UI의 말은 "업데이트"다** (사용자 결정)
- 검토한 대안: 기도제목을 사용자와 1:1로 두고 계속 UPDATE하며 최종 수정일만 보여주기.
- **두 안은 화면에 보이는 결과가 같다.** 편집 폼에 기존 내용을 채워 열고 저장할 때 새 행을
  만들면 `created_at`이 갱신되므로 "○일 전"이 그대로 동작한다. 차이는 저장 방식뿐이다.
- append-only를 고른 이유 둘. (1) **이력이 공짜로 남는다** — "응답된 기도 돌아보기"는 이
  앱과 잘 맞는 후속인데 1:1 UPDATE는 그것을 영구히 버린다. (2) **스키마 변경이 0이다** —
  1:1로 가면 `type='prayer'`에 걸리는 부분 유니크가 필요하고,
  *"작성 화면이 나눔과 동일해 별도 테이블을 두지 않는다"*(`init-db.sql:110`)는 근거가 무너진다.
- ⚠️ **화면의 말은 "수정"이 아니라 "업데이트"다.** 저장이 append-only인데 "수정"이라고
  하면 말과 동작이 어긋난다. 실제로 새로 쌓이는 것이므로 "업데이트"가 정확하다.
- 내 기도제목 이력을 **본인만 보는 목록은 MVP에서 뺀다.** 데이터는 이미 쌓이므로 나중에
  화면만 붙이면 된다.
- 결과: 확정. `sharings(type='prayer')` + `ORDER BY created_at DESC LIMIT 1` 그대로.

**✅ D-1707. 가입에는 리더 승인이 필수다** (사용자 결정)
- 왜: 초대 코드가 곧 입장 권한인데 **단톡방에 뿌린 링크는 어디로든 퍼진다.**
  기도제목은 이 앱에서 가장 사적인 데이터라(D-1004) 링크를 주운 사람이 그대로 들어오면 안 된다.
- 흐름: `/invite/{code}` → 로그인 없이 방 이름 확인(D-1005) → 로그인 →
  **"가입 신청"** → `pending` 행 생성 → 리더의 멤버 목록에 "승인 대기 N명" → 승인/거절.
- **`pending`은 방 내용을 하나도 못 본다.** 그것이 승인의 존재 이유다. 절반만 보여주면
  승인이 아무것도 막지 못한다.
- 리더는 `communities.created_by`가 자동으로 `role='leader'`. **위임·복수 리더는 MVP 제외.**
- ⚠️ **승인 대기를 푸시 알림에 걸면 MVP에서 동작하지 않는다.** 알림 도메인·PWA 푸시가
  Phase 3다. 멤버 목록의 배지로만 알린다 — D-903이 똑같이 데인 지점이다.
- ⚠️ 부작용: 초대받은 사람이 리더가 승인할 때까지 못 들어오므로 **D-802("실제 사람들로
  채운다")가 더 느려진다.** 초기에는 리더가 본인이라 감당된다.
- 결과: 확정. `community_members.status` 컬럼을 새로 둔다.

**✅ D-1708. 초대 코드는 `id`와 별개인 회전 가능한 컬럼이다. 재발급만, 만료 없음** (사용자 결정)
- **코드를 방 ID로 쓰지 않는다.** 그러면 재발급이 곧 방을 새로 만드는 일이 되어
  이 결정의 알맹이를 스스로 무너뜨린다. 게다가 `communities.id`는
  `community_members` · `sharing_communities` · `prayer_partners`가 FK로 참조하고 있어
  코드를 PK로 삼으면 **재발급마다 그 전부가 깨진다.**
- 그래서 주소가 둘로 나뉜다 — `/invite/{code}`는 코드로 방을 찾아 `id`를 얻고,
  `/communities/{id}`는 멤버가 쓴다. `id`가 순차 정수로 노출되는 것은 MVP에서 문제가
  아니다: **주소를 추측해도 승인 전에는 아무것도 보이지 않는다**(D-1707).
- **만료를 두지 않는 이유**: 승인이 있으면 코드 유출의 피해가 "가입 신청이 하나 뜬다"로
  줄어든다. 만료는 리더가 관리할 것을 하나 늘리고, 만료된 링크로 들어온 사람을 받는
  화면을 하나 더 부른다. 재발급만으로 충분하다.
- 코드는 추측 불가능하도록 **10~12자 랜덤**.
- 결과: 확정. `communities.invite_code` 컬럼을 새로 둔다.

### 영역 18 — 공동체 화면을 먼저 세우기

**✅ D-1801. 공동체 화면을 목데이터로 먼저 만든다** (사용자 결정)
- 왜: Phase 2의 선행 조건 두 개(백엔드 배포 + `BACKEND_ORIGIN`, CSRF 재활성)는 **화면과
  독립적이다.** 둘을 기다리는 동안 화면이 멈춰 있을 이유가 없고, 반대로 화면이 먼저 서 있으면
  API가 붙을 때 붙일 자리가 이미 정해져 있다.
- 어떻게 갈아 끼우나: `features/community/api.ts` **한 파일**에 목데이터와 접근 함수
  (`listMyCommunities` · `getCommunity`)를 모아 뒀다. 백엔드가 붙으면 이 파일 안만 fetch로
  바꾸고 호출부(page·컴포넌트)는 그대로 둔다 — `features/bible/api.ts`가 로컬 JSON을 감춰 둔
  것과 같은 구조다. **목데이터를 컴포넌트에 흩뿌리지 않는 이유**가 그것이다: 지울 때 한 파일만 본다.
- 목데이터에 일부러 **비정상 아닌 빈 상태**를 넣었다 — 기도짝 미배정(`prayerPartner: null`),
  나눔 0건, 승인 대기 2명, 대기 중인 방 하나. 전부 실제로 존재할 상태라 화면이 감당하는지
  지금 봐야 한다.
- 결과: 성공. `/communities` · `/communities/{id}` · `/communities/new` 세 화면.

**✅ D-1802. 프론트 라우트를 `/communities`(복수형)로 통일하고 `/community`를 없앤다**
- 왜: 문서가 이미 `/communities/{id}`를 쓰고(D-1708) API도 `/api/v1/communities`인데,
  탭만 `/community`(단수)였다. 그대로 두면 목록과 대문이 **다른 트리**에 놓여
  `/community`(목록)와 `/communities/{id}`(대문)라는 헷갈리는 짝이 된다.
- 결과: `src/app/community/`(ComingSoonScreen을 쓰던 자리) 삭제, `BottomNav`의 href 변경.
  `ComingSoonScreen`은 `/prayer`·`/sharings/new`가 계속 쓰므로 남는다.

**✅ D-1803. 갈 곳이 없는 링크는 아예 놓지 않는다**
- 무엇을 뺐나: 나눔 자료실의 **"더보기"**(`/communities/{id}/sharings`), 나눔 **상세** 링크.
  둘 다 나눔 도메인(Phase 3)과 함께 생기는 라우트라 지금 놓으면 **404가 된다.**
- ⚠️ 예외를 하나 뒀다. 기도짝의 "기도제목 보기"는 **카드의 존재 이유**라 뺄 수 없어,
  `/prayer`(탭의 "준비 중" 화면)로 보낸다. 거기가 막다른 곳이 아니게 만들어 둔 것이
  `ComingSoonScreen`을 둔 이유였다(D-1602). 기도 도메인이 붙으면 `/prayer/{userId}`로 한 줄만 바꾼다.
- 같은 이유로 **`...`(관리) 버튼도 두지 않았다.** 이름 변경·코드 재발급·강퇴가 전부 쓰기
  API라, 지금 놓으면 눌러도 아무 일도 없는 버튼이 된다. D-1003이 그 자리를 지정해 뒀으므로
  TODO 주석만 남긴다.
- 승인/거절 버튼과 "만들기" 버튼은 **모양을 두고 `disabled` + 한 줄 안내**로 갔다. 이 둘은
  화면의 주 동작이라 빼면 화면이 무슨 화면인지 알 수 없어진다 — 없는 척하는 것보다
  "아직 안 열렸다"고 말하는 편이 정직하다.

**✅ D-1804. 초대는 링크를 클립보드에 넣는 버튼 하나다**
- 왜 그 형태인가: 가입은 초대 링크로만 이뤄지고 공개 검색은 배제됐다(D-1004). 즉 이 버튼
  하나가 **사실상 유일한 유입 경로**다. 그리고 실제 유통 경로가 카톡이라 사용자가 하는 동작은
  "복사 → 단톡방에 붙여넣기"다. 그래서 공유 화면을 한 겹 두지 않고 곧바로 복사한다.
- ⚠️ **오리진을 서버에서 만들지 않고 클릭할 때 `location.origin`에서 읽는다.** 로컬·미리보기·
  프로덕션이 서로 다른 주소라 하나를 환경변수에 박으면 나머지에서 틀린 링크가 복사된다.
- 클립보드 실패 처리는 `CopyVerseButton`과 같다(`lib/clipboard.ts` 재사용) — 보안 컨텍스트가
  아닌 곳에서는 API가 아예 없어 실제로 마주치는 실패다(D-704).

**메모 — 시안과 달라진 곳 둘**

  붙였는데, 이름이 길어지면 제목을 밀어낸다. 이름이 곧 이 카드의 내용이라 자리를 넉넉히 준다.
- 상단바는 **`MainTopBar`에 `title`·`icon`을 열어** 재사용했다. 대문 상단바는 벨과 프로필이
  홈과 똑같은 자리에 똑같이 있고 가운데 글자만 다르다. 따로 만들면 알림 배지를 실데이터로
  바꿀 때(Phase 3) 두 곳을 고치게 된다.

### 영역 19 — 중보기도실 화면

**❌→✅ D-1901. 시안에서 폐기된 것은 세 번째 구역뿐이다** (사용자 정정)
- 무엇을 틀렸나: D-904("공동체 선택 단계를 없앤다")를 **시안 전체를 버리라는 뜻으로 읽었다.**
  그래서 첫 구역 "기도를 요청하세요"까지 지우고, 기도제목 작성 진입점을 화면 **맨 아래**로
  내렸다. 사용자가 잡았다 — "작성 유도는 중보기도실 처음으로 설정하지 않았나?"
- 맞는 독법: `Pray Page.png`는 구역이 셋인데 D-904가 폐기한 것은 **세 번째**(공동체별 목록 →
  드릴다운)뿐이다. 첫 구역은 D-903이 말한 작성 유도의 자리 그 자체라 그대로 산다.
- 왜 맨 위인가: 이 화면에서 **유일하게 "내가 주어"인 자리**다. 아래 두 구역은 전부 남을 위한
  것이라, 내 기도제목을 올리는 입구가 그 뒤로 밀리면 화면의 첫인상이 "남을 위해 뭘 해라"가 된다.
  공동체가 하나도 없어 목록이 비는 날에도 이 구역은 남는다 — 속한 방이 없어도 기도제목은 쓸 수 있다.
- 결과: 구역 셋 = 기도를 요청하세요(민트) / 이번주 기도짝(핑크) / 함께 기도해요(핑크).

**✅ D-1902. 내 기도제목 이력 목록을 MVP에 포함한다** (사용자 제안, D-1706 일부 번복)
- D-1706은 "본인용 이력 목록은 MVP 제외"였다. 사용자가 첫 구역에 메뉴를 두고 "이전 기도제목
  보기"를 넣자고 했고, 확인해 보니 **뒤집을 값어치가 있었다**: `GET /pray/requests/me`는
  **읽기 API라 목데이터로 완전히 동작한다.** 이번 범위에서 `disabled`가 아닌 유일한 새 화면이다.
- append-only를 고른 이유가 "이력이 공짜로 남는다"였는데(D-1706), 그 이력을 볼 자리가 없으면
  공짜로 남긴 것이 아무 데도 쓰이지 않는다.
- 화면이 **맨 위 한 건에 "현재 기도제목" 배지**를 붙인다. 남들에게 보이는 건 그것뿐이라는
  사실(`ORDER BY created_at DESC LIMIT 1`)을 화면이 직접 말하지 않으면 아래 것들도 보이는 줄 안다.
- ⚠️ **`...` 드롭다운은 만들지 않았다.** 시안은 `...`이지만 걸 항목이 하나뿐이고,
  `components/ui/`에 dropdown-menu가 없어 radix 드롭다운을 새로 깔아야 한다. 항목 하나에
  메뉴 한 겹은 탭 수만 늘린다. `CommunitySection`의 `action` 슬롯에 텍스트 링크로 넣었다.
- 라우팅: `requests`가 정적 세그먼트라 `[userId]`보다 먼저 매칭된다. API_SPEC이 `room`/
  `summary`/`requests`를 `{userId}` 자리의 예약어로 정해 둔 것과 **같은 구조가 프론트에서도
  성립한다.** 빌드 라우트 표에서 `/prayer/requests`(정적)와 `/prayer/[userId]`(동적)로 갈리는 것을 확인했다.

**✅ D-1903. 프론트에 공유 목데이터 원장을 두지 않는다** (사용자 결정)
- 검토한 안: `features/_mock/entities.ts`에 `USERS`·`COMMUNITIES`를 모으고 도메인별 `api.ts`가
  참조하게 한다. 동기는 21번 김민수가 `community/api.ts`와 `prayer/api.ts` 양쪽에 존재한다는 것.
- **한 번 만들었다가 되돌렸다.** 반려 이유 셋:
  1. **실패 경로를 못 막는다.** 실제 사고는 "21번이 `members` 배열에 **없어서**" 대문 →
     `/prayer/21`이 404가 나는 것인데, 원장이 막는 것은 이름 오타뿐이고 이름 오타는 404를
     만들지 않는다. 원장 문서에 "존재까지 보장하지는 않는다"라고 직접 써 놓고도 넘어갔었다.
  2. **이미 잘 도는 코드에 회귀 위험을 새로 만든다.** `community/api.ts`를 참조로 바꾸는
     작업이 필요한데, 그 파일이 떠받치는 화면 셋은 이미 검증이 끝나 있었다.
  3. **진짜 DB는 postgres고 조회 주체는 백엔드다.** 프론트에 DB 흉내를 두면 사본이 하나 늘
     뿐이고, 백엔드가 붙을 때 함께 버려진다.
- 대신 남긴 원칙: **목데이터는 테이블 모양이 아니라 API 응답 모양**이다. 조인·정렬·파생값이
  이미 끝난 상태로 손으로 쓴다(`communities`는 조인 결과, `request`는 최신 한 건,
  `prayedByMeToday`는 파생, 배열 순서는 D-1703 정렬 완료). 그래야 "이 파일만 fetch로 바꾸면 끝"이
  성립하고, 프론트에서 계산하기 시작하면 백엔드가 붙을 때 통째로 버려질 코드가 자란다.
  정렬 SQL은 이미 API_SPEC:391-398에 적혀 있다.
- 감수하는 비용: 인물이 두 파일에 중복된다. 검증 항목(대문 → `/prayer/21` 착지)으로 막는다.

**✅ D-1904. "기도했어요"는 눌린 척하지 않는다**
- 로컬 상태로 눌리는 척하는 안을 반려했다. `prayedByMeToday`까지 뒤집어야 하는데 그건 서버
  계산값이라 새로고침하면 사라진다. **기도했다는 기록이 이 앱의 신뢰 그 자체인데 거기서
  거짓말을 하는 셈이다.** `POST /pray/{userId}`는 `/communities/new`의 "만들기"와 같은 문턱
  (백엔드 배포 + CSRF, D-404) 뒤에 있으니 두 화면이 다른 태도를 취할 이유도 없다.
- 다만 **비활성 사유 둘을 구분해서 렌더한다**:
  `prayedByMeToday: true` → "오늘 이미 기도했어요" (**진짜 상태.** 백엔드가 붙어도 그대로 남는다.
  하루 하나라 더 눌러도 변하지 않는다) / 그 외 → `disabled` + "백엔드가 연결되면 열립니다".
- 시안의 **"취소하기"는 그냥 뒤로 가기**다. `POST /pray/{userId}`에 대응하는 DELETE가 없다
  (API_SPEC). standalone PWA엔 브라우저 뒤로가기가 없어(D-1505) 화면 안에 둔다.

**메모 — 날짜를 다루지 않는다**
`daysAgo`를 서버가 숫자로 준다는 계약(API_SPEC) 덕에 날짜 라이브러리도 `lib/date.ts`도
만들지 않았다. 렌더는 삼항 한 줄이고 `createdAt`은 화면에서 파싱하지 않는다 — 파싱하는
순간 클라이언트 시계와 타임존이 따라 들어온다.
예외가 하나 있다. `/pray/requests/me`는 **`daysAgo`를 안 준다**(API_SPEC이 여기만 뺐다).
이력은 연대기 목록이라 "○일 전"보다 절대 날짜가 맞으므로 `createdAt`을 앞 10자만 잘라 쓴다.

**메모 — `MemberName`이 `CommunitySection.tsx`로 이사했다**
공동체 멤버 목록과 기도 카드가 사람을 똑같이 그린다(마스코트 + 이름). `MemberList`에 두면

**✅ D-1905. 카드에는 기도제목을 아예 보여주지 않는다** (사용자 결정, D-903 일부 수정)
- 무엇이 바뀌었나: 초안의 사람 카드는 기도제목 본문을 두 줄 미리보기(`line-clamp-2`)로 깔고
  "○일 전"을 붙였으며, 없는 사람에게는 "아직 기도제목이 없어요"를 적었다. **셋 다 뺐다.**
  카드에 남는 것은 사진 · 이름 · 공동체 · 체크뿐이고, 기도제목은 **들어가야 보인다.**
- 왜: **목록은 누구를 위해 기도할지 고르는 자리지 읽는 자리가 아니다.** 본문이 깔리면 한 화면에
  두세 명밖에 안 들어와 "훑고 고른다"가 성립하지 않는다. 읽는 일은 상세가 한다.
- ⚠️ **문서 두 곳과 부딪혀 문서를 고쳤다.** D-903은 "카드에는 '아직 기도제목이 없어요'를 두고",
  로드맵은 "카드에 '○일 전' 표시"라고 적고 있었다. 코드가 아니라 그 두 줄을 수정했다.
- **D-903의 본체는 살아 있다**: 기도제목이 없는 사람도 목록에 남고, 그 카드로 들어가 기도를
  누를 수 있다(기도의 단위가 사람이라 성립한다 — `prayer_logs`에 `sharing_id`가 없다).
  바뀐 것은 **그 사실을 카드에 적느냐**뿐이다. 작성 유도도 자리를 잃지 않았다 — D-1901이
  화면 맨 위 "기도를 요청하세요" 구역으로 옮겨 뒀다.
- 부수 효과: `daysAgoLabel`을 쓰는 화면이 상세 하나만 남아 `PrayerPersonCard`에서 그쪽으로
  내려갔다. 카드는 이제 `request`를 읽지 않는다(타입에는 남는다 — 상세가 같은 응답을 쓴다).

**✅ D-1906. 기도 관련 강조색은 `accent`다, `destructive`가 아니다**
- 사용자가 버튼·체크를 빨강 계열로 바꾸면서 `bg-destructive/90`, `bg-destructive/50`을 썼다.
  **눈으로는 맞다** — `--destructive`와 `--accent`가 지금 둘 다 `--manna-third`(#ff2d55)다.
- 그런데 의미가 다르다. `destructive`는 삭제·파괴용이라, 나중에 진짜 삭제 버튼(강퇴,
  기도제목 삭제)이 생겨 그 색을 조정하면 **"기도했어요" 버튼이 같이 따라 바뀐다.**
  지금 `accent`로 바꿔 두면 색은 그대로고 나중에 엮이지 않는다.
- 같은 이유로 `text-white`(원시값)가 아니라 `text-accent-foreground`(토큰)를 쓴다.
  globals.css의 주석대로 **컴포넌트는 primitive를 직접 참조하지 않는다.**
- `bg-secondary text-white`는 `variant="secondary"`가 이미 하는 일이라 그걸로 바꿨다 —
  hover 상태까지 딸려 온다.

**색 배분 (2026-09-01 기준)**
| 자리 | 클래스 | 뜻 |
|---|---|---|
| 기도제목 작성하기 | `variant="secondary"` | 청록. **내가 요청하는** 동작 (민트 구역) |
| 기도했어요 | `bg-accent text-accent-foreground` | 빨강. **내가 기도하는** 동작 (핑크 구역) |
| 오늘 이미 기도했어요 | `bg-accent/20` | 같은 빨강의 옅은 판 — 이미 한 상태 |
| 카드 체크 | `bg-accent/50` / `text-accent/50` | 채워진 것과 옅은 것으로 갈린다 |
구역 배경색과 버튼색이 짝을 이룬다 — 민트 구역엔 청록, 핑크 구역엔 빨강.

**✅ D-1907. 정렬 2순위로 "기도제목이 최신인 사람 먼저"를 넣는다** (사용자 결정, D-1703 보강)
- 바뀐 것: `latest_request_at DESC NULLS LAST`가 1순위(오늘 내가 안 한 사람)와
  2순위(적게 받은 사람) **사이에** 들어갔다. 구획 셋 모두에 같은 규칙이 적용된다.
- 왜: **급한 기도제목을 방금 올렸는데 목록 바닥에 있으면 올린 의미가 없다.** 기도제목은
  갱신되는 것이고, 갱신은 "지금 이게 필요하다"는 신호다. 그 신호가 순서에 반영되지 않으면
  중보기도실이 정적인 명부가 된다.
- **이름순 반려(D-1703)에는 해당하지 않는다.** 이름순이 위험했던 이유는 순서가 **고정**이라
  앞사람만 계속 기도받는다는 것이었다. 최신순은 업데이트하면 올라가므로 순환한다.
- ⚠️ **D-903과 부딪히는 지점을 알고 넣었다.** `NULLS LAST`라 기도제목이 없는 사람이 각
  구간의 바닥으로 간다 — D-903이 걱정한 "조용한 사람이 배제된다"에 가까워진다.
  그래서 `recent_received ASC`를 **3순위로 남겼다**: 기도제목이 없는 사람들끼리는 여전히
  "적게 받은 사람 먼저"가 작동해, 바닥에서의 순서까지 고착되지는 않는다.
  작성 유도도 자리를 잃지 않았다 — 화면 맨 위 구역이다(D-1901).
- 서버 부담 없음: `latest_request_at`은 응답의 `request.createdAt`과 같은 값이라 새로
  계산할 것이 없다. 단 `sharing_communities` 조인 **뒤에** 잡은 값이어야 한다
  (= 내가 볼 수 있는 것 중 최신).
- 목데이터도 이 순서로 다시 깔았다: 22(오늘) → 41(2일) → 21(4일) → 23(없음) →
  **24(12일, 이미 기도함)** → 42(없음, 이미 기도함).

**메모 — 상세의 "○일 전"이 오른쪽으로**
기도제목 본문 아래 왼쪽에 있던 것을 오른쪽 정렬로 옮겼다(사용자 요청). 본문이 왼쪽에서
시작하므로 메타 정보를 반대쪽 끝에 두면 둘이 섞여 읽히지 않는다.

**✅ D-1908. 정렬을 "기도제목 최신순 → 내가 오래 안 한 사람" 두 키로 바꾼다** (사용자 결정)
- D-1907로 네 키가 됐던 것을 **세 키로 줄였다.** `recent_received`(그 사람이 모두에게서 최근
  7일간 받은 수)가 통째로 빠지고, `last_prayed_by_me`(내가 마지막으로 이 사람에게 기도한 날)로
  대체됐다. "오늘 내가 했나"는 그 값의 특수한 경우라 흡수됐다.
- **왜 `recent_received`를 버렸나** (사용자 지적): 계산이 아니라 **전원에게 같은 순서를 준다는
  것**이 문제였다. 모두가 같은 사람을 맨 위에서 보고 → 그 사람에게 기도가 몰리고 → 다음
  새로고침엔 아래로 꺼지고 → 다음 사람에게 몰린다. 공평해지라고 넣은 키가 쏠림을 만든다.
  내 기준으로 바꾸면 **목록이 사람마다 달라지고**, 각자가 자기가 소홀했던 사람을 챙기는 것의
  합이 오히려 더 고르게 퍼진다.
- 덤: **"최근 7일"이라는 근거 없는 숫자가 사라졌다.** API_SPEC이 스스로 "근거가 없는 숫자다"라고
  적어 둔 값이었다. `max(prayed_on)`은 창을 쓰지 않는다.
- ~~키 순서는 최신순이 위다~~ → **D-1909에서 되돌렸다.** 최신순을 맨 위에 두면
  "오늘 기도했으면 아래로"가 사라져, 이미 기도한 사람이 최신 기도제목을 갖고 있으면 계속
  맨 위에 남는다. 그건 중보기도실이 하는 일이 아니다. 아래 D-1909 참고.
- **스키마가 인덱스 하나 늘었다**: `idx_prayer_logs_by_me(pray_by, prayed_for_user_id, prayed_on)`.
  기존 `idx_prayer_logs_target_day`는 받는 사람 기준이라 `pray_by = :me` 필터를 못 탄다.
  대신 전 사용자 집계가 사라져 쿼리 자체는 더 싸다.

**✅ D-1909. 1순위는 다시 "오늘 내가 기도했나"다** (사용자 결정, D-1908 키 순서 정정)
- D-1908에서 최신순을 맨 위로 올렸다가 **하루 만에 되돌렸다.** 그러면 이미 기도한 사람이
  최신 기도제목을 갖고 있는 한 계속 목록 맨 위에 남는다. 중보기도실은 **오늘 아직 기도하지
  않은 사람을 찾는 화면**이라, 그 구분이 다른 무엇보다 위에 있어야 한다.
- 최종 네 키:
  1. `prayed_today_by_me ASC` — 목록을 크게 둘로 가른다
  2. `latest_request_at DESC NULLS LAST` — 그 안에서 기도제목이 최신인 사람 먼저 (D-1907)
  3. `last_prayed_by_me ASC NULLS FIRST` — 내가 오래 안 한 사람 먼저 (D-1908)
  4. `u.id ASC` — 타이브레이커
- **2번이 `TIMESTAMPTZ`(초 단위)라 기도제목이 있는 사람은 거기서 다 갈린다**(사용자 지적).
  그래서 3번은 실질적으로 **기도제목이 없는 사람들끼리의 순서**만 정한다. 값어치가 없어
  보이지만 그 자리가 정확히 D-903이 지켜지는 곳이다 — 빼고 `u.id`로만 두면 그 무리의 순서가
  영구히 고정돼, D-1703이 이름순을 반려한 것과 같은 함정에 빠진다.
- 3번의 `prayed_on`은 `DATE`라 같은 날이면 동점이고, 4번이 그것을 받는다. 네 키가 다 일한다.

**✅ D-1910. 오늘 기도한 뒤 그 사람이 기도제목을 바꿔도 체크는 풀지 않는다** (사용자 결정)
- 물음: 내가 A를 위해 기도한 뒤, 같은 날 A가 기도제목을 갱신하면? A는 이미 아래 무리에 있어
  새 기도제목이 내 눈에 안 들어온다.
- 결정: **무시한다. 기도 여부는 다음 날 초기화된다.**
- 왜: `prayer_logs`의 UNIQUE 키가 `(prayed_for_user_id, pray_by, prayed_on)`, 즉 **날짜 단위**다.
  갱신으로 체크를 풀면 하루에 두 번 기도한 것이 되어 그 제약이 깨지고, "어제 N명"이 사람 수가
  아니게 된다(D-901).
- 더 근본적으로 **체크의 뜻이 "이 글을 읽었다"가 아니다.** "오늘 이 사람을 위해 기도했다"이고,
  기도의 단위가 사람이라(D-303, `prayer_logs`에 `sharing_id`가 없다) 제목이 바뀌어도 그 사실은
  변하지 않는다.
- 그날 안에 올라온 급한 기도제목을 알리는 일은 **알림 도메인(Phase 3)의 몫이지 정렬의 몫이
  아니다.** 정렬로 풀려면 `prayer_logs.created_at`과 `sharings.created_at`을 비교하는 키가
  하나 더 붙고, 카드에 "갱신됨" 표시까지 필요해진다.

### 영역 20 — 상단바가 화면마다 다르게 행동하던 문제

**✅ D-2001. 상단바는 전 화면 sticky다** (사용자 지적)
- 무엇이 문제였나: `BibleHeader`만 `sticky top-0 z-30`이고(D-101), 나머지 전 화면이 쓰는
  `MainTopBar`는 평범한 흐름 요소라 스크롤하면 위로 사라졌다. **한 앱에서 상단바가 화면마다
  다르게 행동한다**는 것이 사용자가 먼저 알아챈 증상이다.
- 결과: `MainTopBar`에 성경 헤더와 **같은 sticky·같은 z-30**을 줬다. 값을 맞춘 이유는
  둘이 같은 것이어야 하기 때문이지 우연이 아니다.
- 부수: 상단바가 사라지지 않으니 그 자리의 색도 사라지지 않는다 — 아래 D-2002가 성립하는
  전제이기도 하다. 헤더가 스크롤로 걷히면 상태바 색만 남아 화면과 어긋난다.

**✅ D-2002. 상태바(시계·배터리 뒤)를 칠하는 수단은 `theme-color` 하나뿐이다**
- 무엇이 문제였나: `app/layout.tsx`가 문서 theme-color를 `BRAND_COLOR`(#FFCC00, 노랑)로
  **못박고 있었다.** iOS 15+ standalone PWA는 상단 safe area를, Android Chrome은 시스템
  상태바를 이 값으로 칠한다. 그래서 크림색 홈이든 민트색 성경이든 **시계·배터리 아이콘 뒤는
  늘 노랑**이었다. "색이 프레임 위까지 안 이어진다"는 말의 실체가 이것이다.
- 결과: 루트 기본값을 `SURFACE_COLOR.warm`으로 낮추고, 성경·기도는 **세그먼트 layout**에서
  덮어쓴다. 페이지마다 `export const viewport`를 흩뿌리지 않는 이유는 탭에 페이지가 늘어도
  자동으로 따라오게 하기 위해서다. `/communities/*`는 루트 기본값과 같아 layout이 없다.
- **매니페스트의 `theme_color`는 건드리지 않았다.** 그건 설치 후 스플래시 색이고, 이건
  화면이 켜져 있는 동안의 상태바 색이다. 둘이 같은 값일 이유가 없다.

**❌ D-2003(폐기). `viewport-fit=cover` + `black-translucent`로 직접 칠하기**
- 왜 시도할 만했나: 웹 콘텐츠를 상태바 아래까지 밀어 넣고 헤더 배경으로 노치까지 직접
  칠하는 방식이라, CSS만으로 완전히 통제된다.
- 실패 이유: **그 모드는 상태바 글자를 흰색으로 강제한다.** 우리 상단바 셋(#fdfcf0 ·
  #f0fffe · #ffeff2)이 전부 밝은 파스텔이라 시계와 배터리가 안 보이게 된다. 사용자가 원한
  것은 "아이콘도 같이 영향을 받는 것"이지 "아이콘이 사라지는 것"이 아니다.
- 덤으로 모든 헤더·네비에 `env(safe-area-inset-*)` 계산이 붙었을 것이다. 반려로 그 코드가
  통째로 없어졌다.

**✅ D-2004. 상단바 색은 새로 만들지 않고 `--surface-*` 셋을 그대로 쓴다**
- warm(#fdfcf0) = 홈·공동체·로그인·랜딩·404 · cool(#f0fffe) = 성경 · love(#ffeff2) = 기도.
  globals.css가 이미 도메인별로 나눠 둔 그 셋이고, 홈 섹션 카드가 쓰는 색과 같다.
- `MainTopBar`의 기존 `bg-muted`는 `--surface-warm`과 **값이 같다.** 그래서 홈·공동체는
  눈에 보이는 변화가 없고 의미만 도메인 색으로 정리됐다.
- `BibleHeader`는 손대지 않았다. `bg-header`는 장 제목 밴드(`ChapterSection`)와 토큰을
  공유해야 하고(D-101), 값은 어차피 `--surface-cool`과 같다.

**✅ D-2005. 기도 상단바는 연분홍(`--manna-third-light`)이지 진한 빨강이 아니다** (사용자 결정)
- 사용자가 "붉은 색 계열"이라 했고 후보는 둘이었다 — `--manna-third`(#ff2d55)와
  `--manna-third-light`(#ffeff2).
- 연한 쪽을 골랐다: **밝은 배경이라야 iOS가 상태바 글자를 검정으로 두어 시계와 배터리가
  읽힌다.** 상태바 글자색은 우리가 고를 수 없는 값이라, 색 선택이 곧 가독성 선택이다.
- 의미로도 맞다. D-1906이 정한 배분에서 진한 `accent`는 **동작**("기도했어요" 버튼)의 색이다.
  상단바는 동작이 아니라 위치 표시라 같은 계열의 옅은 판이 맞다.

**⚠️ D-2006. 상단바 `tone`과 라우트 `themeColor`는 손으로 짝을 맞춰야 한다**
- CSS 변수는 매니페스트·meta에서 읽히지 않아(`lib/brand.ts`가 이미 안고 있던 제약) 같은 색이
  두 곳에 hex와 토큰으로 따로 적힌다. 한쪽만 바꾸면 **상단바와 상태바 사이에 색 경계선**이
  생긴다 — 고치려던 것이 정확히 그것이다.
- 자동화 대신 세 파일(`brand.ts`의 `SURFACE_COLOR`, `MainTopBar`의 `TONE`, 세그먼트 layout)에
  서로를 가리키는 주석을 달아 뒀다. 색이 셋뿐이라 지금은 이걸로 충분하다.

**✅ D-2007. 하단 네비 아래 여백 8 → 24px** (사용자 지적)
- 왜: `py-2`라 아래위가 같았고, **화면 맨 아래 모서리는 엄지가 닿기 나쁜 자리**라 탭 영역이
  거기서 끝나면 안 된다. `pt-2 pb-6`으로 아래만 두껍게.
- 네비 높이 68 → 84px. 본문 여백은 안 고쳤다 — 각 화면의 `pb-28`(112px)과 리더의
  `pb-32`(128px)가 84px를 여전히 덮는다.
- `env(safe-area-inset-bottom)`은 쓰지 않았다. `viewport-fit=cover`가 없으면 그 값이 **0**이라
  지금보다 나빠진다. D-2003을 폐기한 이상 이 함수는 이 앱에서 쓸 수 없다.

**메모 — 검증 한계**
`theme-color` 값이 라우트마다 바뀌는 것은 프로덕션 빌드에 curl로 확인했다(`/`→#FDFCF0,
`/bible/gn/1`→#F0FFFE, `/prayer`→#FFEFF2). 하지만 **그것이 실제로 노치를 칠하는지는
데스크톱에서 검증이 불가능하다** — 상태바 자체가 없다. D-107·D-1307에 이어 세 번째 같은
자리이므로, 실기기(아이폰) 홈 화면 추가 후 확인이 최종 기준이다.

### 영역 21 — iOS 고무줄이 상단바를 끌고 내려가던 문제

**⚠️ D-2101. sticky로는 부족했다 — iOS는 fixed·sticky를 고무줄에 같이 태운다** (사용자 지적)
- D-2001에서 상단바를 전 화면 sticky로 만들고 D-2002에서 상태바 색까지 맞췄는데, 화면을
  아래로 당기면 **상단바가 상태바에서 떨어져 나오고 그 사이에 흰 틈**이 생겼다.
- 원인: iOS 고무줄 스크롤은 문서 전체를 옮기고, `position: fixed`도 `sticky`도 예외가 아니다.
  드러나는 것은 `<body>` 배경(흰색)이라 theme-color를 맞춰 놔도 소용이 없다.
- 즉 **D-2002가 반쪽이었다.** 상태바 색은 맞췄지만 상단바가 거기서 떨어지는 것은 색의
  문제가 아니었다.

**✅ D-2102. 문서를 잠그고 스크롤을 본문에 준다 — `AppShell`** (사용자 제안:
"튕겨도 그 아래부터만 끌 수 있게 하면 안 돼?")
- 무엇을 했나: 화면을 `fixed inset-0`인 flex 컬럼으로 감싸고 **가운데 `<main>`만
  `overflow-y-auto`** 로 둔다. 상단바와 하단 네비는 스크롤러 바깥이라 애초에 움직일 수 없다.
  문서 잠금은 `html:has([data-app-shell]) { overflow: hidden }`.
- 왜 색이 아니라 구조인가: **문서가 안 움직이면 문서가 튕길 것이 없다.** 튕김은 `<main>`
  안에서 일어나고, 그건 사용자가 원한 바로 그 동작이다("그 아래부터만").
- `min-h-0`이 빠지면 아무것도 안 된다 — flex 컬럼에서 그게 없으면 `flex-1` 자식이 콘텐츠
  높이만큼 부풀어 스크롤러가 생기지 않는다.
- **`fixed inset-0`으로 둔 이유**는 `h-full`이 아니라 이것이어야 `:has()`를 모르는 구형
  Safari(15.4 미만)에서도 레이아웃이 성립하기 때문이다. 거기서는 문서 잠금만 안 걸려
  예전처럼 튕긴다 — 기능이 없어질 뿐 화면이 깨지지는 않는다.
- 부수 효과: `pb-28` + `fixed inset-x-0 bottom-0 z-30` **복붙 8벌이 사라졌다.** 하단 네비가
  흐름 안으로 들어오면 본문을 그만큼 비워 둘 이유가 없다. 코드가 준 것보다 줄었다.
- `MainTopBar`에서 D-2001이 넣었던 `sticky top-0 z-30`을 뺐다. 셸 바깥에 있으니 sticky가
  할 일이 없다 — **구조가 대신하는 것을 CSS로 한 번 더 말할 필요는 없다.**

**✅ D-2103. 성경 리더만 셸에서 제외한다**
- 왜: `ChapterFeed`와 `useHideOnScroll`이 `window.scrollY` / `window.scrollTo` / window 스크롤
  이벤트 / 뷰포트 루트 IntersectionObserver로 짜여 있다. 스크롤러를 컨테이너로 바꾸면
  **D-1101~1105로 겨우 잡은 스크롤 튐**과 D-1401~1406(시트 위치), D-1501~1511(뒤로/앞으로)이
  전부 다시 열린다. 상단바 색을 맞추는 작업이 리더 스크롤 재설계를 끌고 들어올 이유가 없다.
- **grep으로 확인하고 결정했다**: window 스크롤을 쓰는 곳은 리더 전용 두 파일뿐이고,
  나머지 11개 화면은 하나도 쓰지 않는다. 그래서 나머지만 안전하게 옮길 수 있었다.
- 리더의 고무줄 틈은 대신 **색으로 덮는다** — `BibleHeader`에 `header-bleed`. 헤더 위쪽으로
  `::before`를 100vh 깔고 `background: inherit`로 헤더 색을 그대로 따라가게 했다. 색을 두 번
  적지 않는 것이 요점이다. 헤더가 `sticky`(=positioned)라 그 `::before`의 컨테이닝 블록이 된다.
- 리더에서 이 틈이 잘 안 보였던 이유도 있다 — 위로 스크롤하면 이전 장이 붙어(D-104)
  문서 맨 위에 닿는 일 자체가 드물다. `/bible/gn/1`에서는 닿는다.

**✅ D-2104. 내부 스크롤러의 대가를 갚는다 — 스크롤 위치 복원** (사용자 결정)
- Next의 스크롤 복원은 `window`에만 걸려서, 내부 스크롤러는 뒤로가기에 맨 위로 리셋된다.
  중보기도실이 "목록에서 사람 고르기 → 기도 → 돌아오기"를 반복하는 화면이라(D-904, 기도의
  단위가 사람이다) 그대로 두면 매일 거슬린다. **고무줄 버그를 스크롤 버그로 바꾸는 셈**이라
  같이 처리했다.
- `sessionStorage`에 `usePathname()` 키로 저장/복원한다. `jump-history.ts`가 이미 쓰는
  도구와 같다 — 리더가 떠날 때 위치를 기억하는 것(D-1508)과 문제도 해법도 같은 모양이다.
- 언마운트 시 `el.scrollTop`을 읽지 않고 `onScroll`이 갱신해 둔 ref를 쓴다. cleanup 시점에는
  엘리먼트가 이미 DOM에서 빠져 있을 수 있다.
- **남긴 한계(`ponytail:` 주석)**: 탭을 다시 눌러 같은 경로로 들어와도 복원된다. "뒤로가기일
  때만"을 가르려면 내비게이션 타입이 필요한데 App Router가 주지 않는다. 같은 탭을 다시
  누르는 일이 드물어 그대로 뒀다.

**✅ D-2105. 하단 네비는 `topBar` 유무로 갈린다 — prop을 하나 더 두지 않는다**
- 지금 존재하는 모든 화면이 정확히 둘로 갈린다: **탭이 가리키는 곳**(상단바 + 하단 네비)과
  **갇히면 안 되는 곳**(로그인·랜딩·404 — 둘 다 없음). 404가 네비를 안 갖는 것은 원래
  의도였고(D-1601, "길 잃은 화면에서 선택지 넷보다 갈 곳 둘"), 그 규칙이 그대로 성립한다.
- prop을 따로 두면 호출부가 항상 같은 값을 두 번 적게 된다. 예외가 생기면 그때 만든다.
- 로그인·랜딩·404도 같은 셸로 잠갔다(사용자 결정). `<main>`이 통째로 `bg-muted`라 당기면
  크림색 위로 흰 틈이 뜨던 것이 같은 병이었다.

**메모 — 검증 한계 (네 번째)**
데스크톱에는 고무줄이 없어 이 작업의 본론은 여기서 검증할 수 없다. 확인한 것은 라우트 11개가
셸을 렌더하고(`data-app-shell`) 리더만 안 쓴다는 것, `html:has([data-app-shell]){overflow:hidden}`과
`.header-bleed::before`가 실제 CSS 번들에 들어갔다는 것까지다. **상단바가 상태바에서 안
떨어지는지는 실기기(아이폰)에서 봐야 한다** — D-107 · D-1307 · D-2002에 이어 네 번째다.

### 영역 22 — 상태바 색이 탭 이동을 안 따라오던 문제 (같은 날 후속)

**⚠️ D-2201. iOS standalone은 `theme-color`를 문서 로드 시점에만 읽는다** (사용자 신고)
- 증상: 상단바 색은 화면마다 맞는데 **상태바(시계·배터리 뒤)만** 성경의 민트로 굳어 있었다.
  홈에서도 공동체에서도 기도에서도.
- 코드는 멀쩡했다 — 라우트마다 `<meta name="theme-color">`가 **정확히 하나씩 올바른 값**으로
  나오고(`/`→#FDFCF0, `/prayer`→#FFEFF2, `/bible/gn/1`→#F0FFFE), RSC 내비게이션 페이로드에도
  같은 값이 실려 온다. 즉 **Next는 제대로 갱신하고 iOS가 안 읽는 것**이다.
- ❌ 먼저 시도한 것: 라우트 변경 때 meta 노드를 head에 다시 꽂아 재평가를 유도(`ThemeColorSync`).
  **실기기에서 효과 없음** — 삭제했다. iOS는 삽입을 신호로 보지 않는다.

**✅ D-2202. 성경 탭만 멀쩡했던 이유가 답이었다 — `redirect()`는 문서 이동이다** (사용자 관찰)
- 사용자가 "성경 들어갈 땐 방식이 좀 다른 거 같은데?"라고 짚었다. 실제로 달랐다:
  `/bible`은 이어읽기 리다이렉트라(D-103) **문서 이동**이 일어난다. Next 문서 그대로 —
  *"When used in a streaming context, this will insert a meta tag to emit the redirect on the
  client side."* 그 문서 로드 시점에 iOS가 theme-color를 다시 읽어 색이 고쳐졌던 것이다.
- **그러니 남은 수단은 문서 이동 하나뿐이다.** 이 한 줄이 이후 결정을 전부 결정했다.

**✅ D-2203. 색이 바뀌는 이동만 문서 이동으로 — `ToneNavigation`** (사용자 결정)
- 대안이던 "상태바 색을 앱 전체에 하나로 통일"은 반려됐다. 사용자 판단: **공동체·나눔·메인 /
  성경 / 기도는 서로 다른 기능 뭉치라 색으로 인덱싱하는 것이 값싸고 한눈에 읽힌다.**
  기능이 늘어날수록 정보 구분에도 유리하다.
- 다만 **색을 지고 가는 것은 상단바지 상태바가 아니다.** 상단바는 폭이 넓고 제목·아이콘과
  같이 읽혀 "여긴 기도 영역"이 전달되지만, 시계 뒤 얇은 띠에서 도메인을 읽는 사람은 없다.
  그 띠의 일은 **아래 바와 어긋나 보이지 않는 것** 하나다. 요구를 그렇게 좁히면 답이 나온다.
- 결정: 톤이 **바뀌는 이동만** `location.assign`으로 돌린다. 홈↔공동체(둘 다 warm, 가장 잦은
  쌍)와 탭 안 이동(`/prayer`→`/prayer/22`)은 그대로 client-side라 빠르다.
- **대가는 이미 지불해 본 값이다**: 성경 탭은 처음부터 문서 이동이었고(D-2202), 세 라운드
  실기기 테스트에서 느리다는 말이 한 번도 안 나왔다. 기도 탭을 성경 탭과 같게 만드는 것뿐이다.
- 링크마다 고치지 않고 **클릭을 한곳에서 가로챈다**. 톤이 바뀌는 링크가 하단 네비 말고도
  흩어져 있다 — 홈의 "최근 읽은 말씀", `PraySummaryRows`, 기도 빈 화면의 "공동체 보러 가기",
  대문의 기도짝 카드, 404의 "성경 읽기". 일곱 곳을 고치고 계속 기억하느니 규칙 한 곳이 작다.
- **캡처 단계여야 한다.** React는 리스너를 루트 컨테이너에 위임하는데 그건 document의
  자손이라, 버블에서는 `<Link>`가 이미 client-side 이동을 시작한 뒤다. 캡처에서
  `stopPropagation`하면 이벤트가 React에 닿지 않는다.
- 새 탭·다운로드·수식키 조합·외부 링크는 가로채지 않는다. 가로채면 브라우저 동작을 망친다.

**✅ D-2204. 앱을 켤 때 노란 상태바는 매니페스트였다** (사용자 신고)
- 증상: 앱을 완전히 껐다 켜면 홈인데 상태바가 **노랑**이었다. 문서 meta는 크림(#FDFCF0)인데도.
- 원인: **iOS standalone은 실행 순간의 상태바 색을 매니페스트 `theme_color`에서 가져온다.**

  이제 `SURFACE_COLOR` 셋과 `BACKGROUND_COLOR` 하나뿐이다.

**✅ D-2205. 라우팅 규칙을 `toneOf` 한 곳으로** (D-2006의 빚 일부 상환)

### 영역 24 — 환경 (셋이 동시에 뜨기까지 걸린 것들)

**📝 brew `postgresql@15`가 Docker Postgres를 가리고 있었다**
- 증상이 배신적이다 — 백엔드는 `FATAL: database "manna_db" does not exist`로 죽는데
  `docker exec manna_postgres psql -d manna_db -c "\dt"`는 12테이블을 멀쩡히 보여준다.
- 원인: brew 인스턴스가 `127.0.0.1:5432`를, Docker가 `*:5432`를 잡아 **둘이 공존**하고
  `localhost`는 brew 쪽으로 간다. 컨테이너 안과 호스트 포트가 서로 다른 서버였다.
- **확인법은 `lsof -nP -iTCP:5432 -sTCP:LISTEN` 한 줄이다.** `postgres`와 `com.docke`가
  같이 나오면 그 상황. `brew services stop postgresql@15`로 닫았다(그 인스턴스는 기본 DB
  3개뿐이었다 — Phase 0 "임시 PG 검증"의 잔재).
- 교훈은 D-704·D-1307과 같은 계열이다: **에러 메시지가 가리키는 곳과 원인이 있는 곳이 다르다.**
  "DB가 없다"는 말에 스키마를 뒤지면 한참 헤맨다.

**📝 `docker compose`(공백)가 안 먹던 것 · 이미지 pull이 막히던 것**
- brew formula `docker` CLI는 플러그인을 `~/.docker/cli-plugins`에서 찾는데 실제 위치는
  `/opt/homebrew/lib/docker/cli-plugins`였다 → `compose`를 인자로 보고 `-d`에서 터진다.
  심볼릭 링크로 해결.
- Docker Desktop이 쓴 `config.json`의 `credsStore: desktop`이 가리키는
  `docker-credential-desktop`이 PATH에 없어 public 이미지 pull까지 막혔다 → 같은 방식으로 링크.
- 둘 다 **brew CLI와 Docker Desktop을 섞어 쓴 데서** 나온다. 레포와 무관한 머신 설정이라
  코드에는 흔적을 남기지 않았다.

**✅ D-2401. 백엔드 폴더는 `apps/backend`. 프로젝트 이름은 `manna-backend` 그대로** (사용자 질문)
- `apps/frontend` ↔ `apps/manna-backend` 비대칭을 없앴다. 참조가 5곳뿐이고 **코드가 그 경로를
  import하지 않는다**(Java 패키지는 `com.manna.backend`라 폴더명과 무관).
- **지금이 가장 싼 시점이라서 지금 했다** — Railway 배포 설정과 GitHub Actions에 경로가
  박히기 전이다.
- `rootProject.name` · `spring.application.name`은 **안 바꿨다.** 그건 파일 위치가 아니라
  산출물·로그의 식별자고, 배포했을 때 `backend-0.0.1-SNAPSHOT.jar`보다
  `manna-backend-...jar`가 무엇인지 말해 준다.
- `run-local.sh` 신규 — `.env`(gitignore됨)의 `GOOGLE_CLIENT_ID/SECRET`을 올리고 `bootRun`.
  시크릿이 비면 먼저 죽으며 이유를 말한다.

**📝 Google Console에서 실제로 등록이 필요한 칸은 하나뿐이다**
- **승인된 리디렉션 URI**에 `http://localhost:3000/login/oauth2/code/google`. 끝이다.
- **승인된 도메인**(브랜딩 탭)은 로컬에 필요 없다 — 스킴·포트를 못 받고 `localhost`는 등록
  자체가 안 되며, 그 칸은 동의 화면에 띄울 홈페이지·약관 링크의 도메인을 받는 자리다.
  세 링크를 비우면 등록할 도메인도 없다.
- `:8080`이 아니라 `:3000`인 근거는 `forward-headers-strategy=framework`다. 직접
  `:8080/oauth2/authorization/google`을 찔러 보면 `redirect_uri`가 `:8080`으로,
  `:3000`을 거치면 `:3000`으로 나온다 — 프록시가 붙인 `X-Forwarded-*`의 차이가 눈에 보인다.

### 영역 25 — `/api/v1/me`가 로그인 직후 500이었다

**✅ D-2402. 연관을 EAGER로 바꾸지 않고 그 조회에만 `@EntityGraph`를 건다**
- 증상: 로그인은 되는데(콜백 성공, `users`·`user_identities`에 행 생성) **화면에 아무 티가
  안 났다.** 사용자가 "로그인 성공 후 로직이 없어서 티가 안 난다"고 말한 그것이 실제로는
  버그였다 — `ProfileButton`은 `/api/v1/me`가 200일 때만 이름을 보여주는데 그게 500이었다.
- 원인: `MeController`가 `identity.getUser()`로 LAZY 프록시를 건드리는데
  `spring.jpa.open-in-view=false`라 컨트롤러에는 영속성 컨텍스트가 없다 →
  `LazyInitializationException`.
- 고친 곳은 `UserIdentityRepository.findByProviderAndProviderUid`에 `@EntityGraph("user")` 한 줄.
- **반려한 두 대안**: (1) `@ManyToOne(fetch = EAGER)` — 이 엔티티를 읽는 *모든* 쿼리에 조인을
  강제한다. (2) `open-in-view=true` — 뷰 렌더링 중에 쿼리가 나가는 것을 되살리는 것이라
  애초에 끈 이유를 되돌린다. **필요한 한 조회에서만 켜는 것**이 맞다. 이 finder를 부르는
  두 곳(`MeController`, `OAuthUserService`)이 **둘 다 곧바로 User를 읽으므로** 손해도 없다.
- ⚠️ **로드맵의 "OAuth 로컬 검증 완료"가 과장이었다**는 기록을 남긴다. 검증된 것은
  *로그인 왕복과 find-or-create*였고 **세션을 읽는 엔드포인트는 한 번도 안 불렸다.**
  쓰기 API를 붙일 때도 같은 함정이 있다 — "저장까지 됐다"와 "화면이 그걸 읽는다"는 다른 검증이다.

### 영역 26 — 프로필 버튼과 마이페이지

**✅ D-2403. 상단바 프로필은 이미지만. 로그아웃은 마이페이지로 내린다** (사용자 결정)
- 그전까지 상단바 우측은 **이름 + 로그아웃 아이콘** 두 칸이었다.
- 내린 이유 둘. (1) 로그아웃이 **늘 한 번 누르면 닿는 자리**에 있었다. (2) 같은 바를 공동체
  대문이 방 이름으로 쓰는데(`MainTopBar`의 `title`), 우측이 두 칸이면 긴 방 이름이 밀린다.
- 그래서 이 버튼은 이제 **상태를 보여주는 일과 거기로 데려가는 일만** 한다.
- `/mypage` 신규. 지금 있는 것은 프로필 이미지 · 이름 · 로그아웃뿐이다. 프로필 수정 ·
  알림 설정 · 내 기도제목 바로가기는 **그 도메인이 붙을 때** 줄을 늘린다.
- **상단바의 프로필이 마이페이지에서 자기 자신을 가리키는 것은 그대로 뒀다.** 이 앱은 이미
  "같은 곳을 가리키는 버튼"을 되돌아가는 수단으로 쓴다(탭을 다시 누르면 그 화면, D-1701).
- 톤은 `warm` — `toneOf()`의 폴백이라 세그먼트 layout의 `themeColor`를 따로 두지 않는다(D-2006).
- 돌아가는 길은 **홈**이다. 탭이 아니라 홈 상단바에서 들어오는 화면이라
  (`/communities/new`의 "취소"와 같은 자리·같은 모양, 가는 곳만 다르다).

**✅ D-2404. 프로필 이미지 호스트는 `next.config.ts`의 `remotePatterns`에 적는다**
- `next/image`는 허용한 호스트만 최적화하고 나머지는 400으로 막는다. Google은
  `lh3.googleusercontent.com`.
- **provider가 늘면 이 목록도 는다**(카카오는 `k.kakaocdn.net`, D-1702). 프로필 이미지가
  기본 아이콘으로만 나오면 여기부터 본다.
- 평범한 `<img>`로 가는 길도 있었지만(허용 목록 유지가 없다) 레포가 이미 `next/image`를
  쓰고 `core-web-vitals` 린트가 그쪽을 본다. 한 줄 늘리는 쪽이 싸다.

**✅ D-2405. 성경 리더 헤더도 같은 `<ProfileButton />`을 쓴다** (사용자 지시 "성경도!")
- 리더 헤더만 **정적 `User` 아이콘**이었다 — 눌러도 아무 일이 없는, 08_USER_FLOWS가 세어 둔
  가짜 어포던스 셋 중 하나.
- 로드맵이 이 교체를 "**인증이 프로덕션에서 살아난 뒤**"로 미뤄 둔 이유는 *"지금 바꾸면 로그인
  자체가 안 되는 화면에 '로그인' 글자만 뜬다"*였다. 그 전제가 오늘 두 군데서 무너졌다 —
  인증이 로컬에서 실제로 돌고(D-2402), 프로필이 데려갈 **목적지**가 생겼다(D-2403).
- 프로덕션에서는 여전히 "로그인"으로 보인다. 하지만 그건 **틀린 표시가 아니라 사실이다** —
  거기서는 정말로 로그인이 안 되어 있다. 미뤄 둘 때 걱정한 것은 "되는데 안 된다고 말하는 화면"
  이었지 "안 되는데 안 된다고 말하는 화면"이 아니었다.
- 상단바 셋(홈·대문·리더) 중 둘이 이제 같은 컴포넌트를 쓴다. 남은 차이는 벨뿐이고,
  그건 알림 도메인이 붙을 때 함께 정리된다(Phase 3).
- **가짜 어포던스가 3곳에서 2곳으로 줄었다** — 상단 벨, 대문 나눔 줄.
