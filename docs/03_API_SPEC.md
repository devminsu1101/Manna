# API 명세서

## 공통 규약

모든 경로는 `/api/v1` 아래. 이 절의 규칙은 **아래 모든 엔드포인트에 적용**되므로 각 명세에서
되풀이하지 않는다.

- **필드는 camelCase.** DB는 snake_case이고 변환은 경계에서 한 번만 한다.
- **인증은 세션 쿠키.** Spring Security 세션을 Next 프록시가 그대로 전달한다. 로그인이
  필요한데 없으면 `401`. 아래 표에서 **비로그인**이라 적힌 하나를 빼고 전부 로그인이 필요하다.
- **쓰기 요청(POST/PUT/PATCH/DELETE)에는 CSRF 토큰**이 필요하다(D-404, D-3101). `XSRF-TOKEN`
  쿠키 값을 `X-XSRF-TOKEN` **헤더**로 보낸다. 없거나 다르면 `403`. 프론트는 쓰기 요청을 전부
  `src/lib/api.ts`의 `apiFetch`로 보내면 이 처리가 자동으로 된다. 폼 파라미터 `_csrf`로
  쿠키 값을 보내면 안 된다 — `csrf.spa()`는 그 자리를 XOR 인코딩 값으로 읽는다.
- **`GET /api/v1/csrf`** (비로그인) — 본문 없이 `204`, `XSRF-TOKEN` 쿠키를 심는다. 쿠키가
  없을 때(첫 방문 · 로그인 직후) `apiFetch`가 알아서 부른다. Next rewrite 경유.
- **에러는 한 가지 형태**다. 성경 엔드포인트가 이미 쓰는 모양을 그대로 쓴다.
  ```json
  { "error": { "code": "NOT_FOUND", "message": "없는 권 또는 장입니다." } }
  ```
- **권한 없음은 403.** 단 **`pending` 멤버가 방 내용을 요청하면 404**를 준다 — 403은
  "그 방이 있긴 하다"를 알려 주는데, 승인 전에는 방의 존재 자체도 노출하지 않는 것이
  D-1707의 취지다.

### Community — 확정 (D-1701~1708)
| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/communities` | 내 공동체 목록 (승인 대기 중인 방 포함) |
| POST | `/communities` | 생성 — 만든 사람이 곧 리더 |
| GET | `/communities/{id}` | 대문 — 기도짝 · 멤버 목록 |
| PATCH | `/communities/{id}` | 이름 변경 (리더) |
| POST | `/communities/{id}/invite-code` | 초대 코드 재발급 (리더) |
| GET | `/invites/{code}` | **비로그인** — 방 이름만 미리 보기 |
| POST | `/invites/{code}/requests` | 가입 신청 → `pending` |
| POST | `/communities/{id}/members/{userId}/approve` | 승인 (리더) |
| DELETE | `/communities/{id}/members/{userId}` | 거절 · 강퇴 · 내가 나가기 |

> **거절·강퇴·나가기가 한 엔드포인트인 이유**: 셋 다 하는 일이 "그 `community_members` 행을
> 지운다"로 **동일하다.** `status`가 `pending`이면 거절, `active`면 강퇴로 읽힐 뿐이고,
> 나가기는 대상이 자기 자신인 경우다. 나누면 본문이 똑같은 핸들러가 셋이 된다.

### Pray — 확정 (D-1703~1706)

하단 탭 "기도하기"에 속한 것을 **접두사 `/pray` 하나로** 묶는다.

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/pray/room` | 중보기도실 카드 목록 (**정렬된 상태로** 내려온다) |
| GET | `/pray/summary` | 메인 최상단 카드 — 어제 받은 수 + 이번 주 기도짝 |
| GET | `/pray/requests/me` | 내 기도제목 **이력** |
| POST | `/pray/requests/me` | 새 기도제목 — 이력에 쌓는다 |
| GET | `/pray/requests/{userId}` | 그 사람의 **최신** 기도제목 (상세 화면) |
| POST | `/pray/{userId}` | 그 사람을 위해 **기도했어요** |

> **이름이 둘로 갈리는 이유.** 이 도메인에는 성격이 다른 두 가지가 있다 —
> **기도제목**(사람이 쓴 내용, `sharings(type='prayer')`)과 **기도 행위**(한 사람이 다른
> 사람에게 한 일, `prayer_logs`)다. 테이블도 의미도 다르므로 `/pray/requests/...`와
> `/pray/{userId}`로 나눈다. 둘을 한 이름에 밀어 넣으면
> `/prayers/{userId}/pray` 같은, 같은 말이 두 뜻으로 겹치는 주소가 나온다.
>
> **`/pray/requests/me`가 컬렉션인 이유.** 본인은 자기 기도제목 **이력**을 본다(D-1706).
> 저장이 append-only라 목록이 실제로 쌓이므로 이 주소는 컬렉션이 맞고, 그래서
> **`POST`가 컬렉션에 하나 추가하는 정통 형태**가 된다. 작성 폼은 이 목록의 첫 항목을
> 채워 넣는다. 이력 화면 자체는 MVP에서 빼지만 **주소는 지금 맞게 잡아 둔다.**
>
> ⚠️ **`room` · `summary` · `requests`는 `{userId}` 자리의 예약어다.** Spring MVC는 리터럴
> 경로를 경로 변수보다 먼저 매칭하므로 동작에는 문제가 없지만, **이 셋과 겹치는 이름을
> 나중에 사용자 식별자로 쓸 수 없다.** `{userId}`는 숫자라 실제로 부딪힐 일은 없다.
>
> ⚠️ 초안의 `POST /prayers/{id}/pray`에서 `{id}`는 기도제목이었다. 기도의 단위가 **사람**이
> 됐으므로(`06_ERD.md`) `{userId}`로 바로잡는다. 어느 제목을 보고 눌렀는지는 기록하지 않는다.
>
> **기도짝 전용 엔드포인트는 두지 않는다.** 초안의 `GET /prayers/partner`를 없앤다. 기도짝은
> 화면 **두 곳**에 나오는데 둘의 값이 다르다 — 대문은 **그 방의** 짝(`GET /communities/{id}`의
> `prayerPartner`), 메인은 **내 모든 방의 짝 중 하나**(`GET /pray/summary`의 `partner`)다.
> 각자 그 화면의 응답에 실려 오므로 전용 경로가 따로 필요 없다.
> ⚠️ **둘을 같은 값으로 보고 한쪽을 지우면 안 된다.** 그러면 메인이 그릴 수 없게 된다.
> 배정 스케줄러가 Phase 3이라 그때까지 양쪽 다 비어 있다.

### Sharing (나눔) — 초안 (Phase 3)

|---|---|---|
| POST | `/sharings` | 초안 — 타입 3종 |

## 확정된 스키마

### GET /api/v1/bible/{book}/{chapter}

성경 한 장을 읽는다. 프론트엔드가 현재 Next 라우트 핸들러로 구현해 쓰고 있으며
(`apps/frontend/src/app/api/v1/bible/[book]/[chapter]/route.ts`), 백엔드는 **이 응답 형태를
그대로** 구현하면 된다. 그러면 프론트는 `NEXT_PUBLIC_BIBLE_API_BASE_URL` 하나만 바꾸면 전환된다.

**Path 파라미터**

| 이름 | 타입 | 설명 |
|---|---|---|
| `book` | string | 권 약어. `books.abbreviation`. 예: `gn`, `ps`, `1co`, `re` |
| `chapter` | int | 장 번호. 1부터 `books.total_chapters`까지 |

**200 응답** — 필드는 모두 camelCase (DB는 snake_case, 변환은 경계에서)

```json
{
  "book": {
    "abbrev": "gn",
    "name": "창세기",
    "order": 1,
    "totalChapters": 50
  },
  "chapterNum": 3,
  "verses": [
    { "verseNum": 1, "text": "그런데 뱀은 여호와 하나님이 지으신 들짐승 중에 가장 간교하니라 ..." },
    { "verseNum": 2, "text": "여자가 뱀에게 말하되 동산 나무의 열매를 우리가 먹을 수 있으나" }
  ]
}
```

| 필드 | DB 대응 |
|---|---|
| `book.abbrev` | `books.abbreviation` |
| `book.name` | `books.name` (한글 권 이름) |
| `book.order` | `books.canonical_order` (정경 순서 1~66) |
| `book.totalChapters` | `books.total_chapters` |
| `chapterNum` | `chapters.chapter_num` |
| `verses[].verseNum` | `verses.verse_num` |
| `verses[].endVerseNum` | `verses.end_verse_num` (없으면 필드 자체를 생략) |
| `verses[].text` | `verses.text` |

**번역본** — 개역개정. 아래 두 가지는 손상이 아니라 정본의 표기이므로 클라이언트가 감당해야 한다.

**1) 절 번호는 장 안에서 1..N으로 이어지지 않는다.** 배열 인덱스로 번호를 유도하면 안 된다.
개역개정은 사도행전 24장에서 6하반~8상반을 들어내어 **7절이 존재하지 않는다**(6절 본문이
`(6하반-8상반 없음)`이라고 직접 밝힌다). 전 성경에서 이 한 곳뿐이지만, 인덱스로 계산하면
그 장의 번호가 통째로 밀린다.

```json
{ "verseNum": 6, "text": "그가 또 성전을 더럽게 하려 하므로 우리가 잡았사오니 (6하반-8상반 없음)" },
{ "verseNum": 8, "text": "당신이 친히 그를 심문하시면 우리가 고발하는 이 모든 일을 아실 수 있나이다 하니" }
```

**2) 여러 절이 한 단락으로 묶인 곳이 11군데 있다.** 이때만 `endVerseNum`이 붙는다.
화면에는 `18-19`로 보여준다 — 시작 번호만 찍으면 다음이 20이라 절이 빠진 것처럼 읽힌다.
식별자(`toVerseId`)는 시작 번호로 만든다.

```json
{ "verseNum": 18, "endVerseNum": 19, "text": "여호와께서 보시기에 정직하고 선량한 일을 행하라 ..." }
```

해당 위치: 신 6:18-19, 신 15:4-5, 신 30:9-10, 대상 16:12-13, 시 92:1-3, 시 105:5-6,
렘 32:3-5, 렘 33:10-11, 겔 24:4-5, 행 15:25-26, 롬 9:1-2.

또한 사본상 생략된 절 13곳(마 17:21, 18:11, 23:14 / 막 9:44, 9:46, 11:26, 15:28 /
눅 17:36, 23:17 / 행 8:37, 15:34, 28:29 / 롬 16:24)은 번호를 유지한 채 `text`가 `(없음)`이다.
빈 문자열이 아니라 실제 본문이므로 그대로 렌더한다.

**404 응답** — 없는 권이거나 장 번호가 범위 밖일 때

```json
{ "error": { "code": "NOT_FOUND", "message": "없는 권 또는 장입니다." } }
```

**캐시 헤더**

```
Cache-Control: public, max-age=86400, stale-while-revalidate=31536000
```

`immutable`을 쓰지 않는다. 불변인 것은 성경 본문이지 우리가 저장한 데이터가 아니다.
실제로 원본을 통째로 갈아엎은 적이 있다 — 이전 개역한글 소스는 27개 권에서 장 끝 절이 잘려
155절이 없었고, 욥기는 36장이 통째로 빠져 그 뒤 장 번호가 하나씩 밀려 있었다.
URL이 배포마다 동일하므로 `immutable`이면 이미 읽은 클라이언트에 수정본이 최대 1년간
도달하지 못한다. 그 사이 사용자는 잘못된 장 번호를 계속 본다. SWR은 성능은 동일하면서
24시간 내에 자가 치유된다.

**호출 패턴** — 리더는 장이 끝나갈 때 다음 장을 미리 부른다(연속 스크롤). 첫 장은 서버 렌더로
내려가므로 이 엔드포인트를 타지 않는다.

### Community

#### GET /communities — 내 공동체 목록

각 줄은 **이름 + 인원 수만**이다(D-1002). "새 나눔 3건" 같은 지표는 데이터가 쌓인 뒤에야
의미가 생기고 지금 붙이면 전부 0이다. 배지를 얹을 자리는 남겨 둔다.

```json
{
  "communities": [
    { "id": 3, "name": "2026-2기 수요 새가족반", "status": "active",
      "memberCount": 12, "role": "leader", "pendingCount": 2 },
    { "id": 7, "name": "푸른교회 수도권지부", "status": "pending" }
  ]
}
```

- **`status: "pending"`인 방도 준다.** 신청한 사실이 안 보이면 사용자는 신청이 안 된 줄 알고
  또 신청한다. 다만 그 줄에는 **`memberCount`를 주지 않는다** — 인원 수도 방의 내용이고,
  `pending`은 아무것도 못 본다(D-1707). 이름은 이미 초대 페이지에서 본 것이라 무방하다.
- `memberCount`는 **`active` 멤버만** 센다.
- `role` · `pendingCount`는 리더에게만 나간다. 멤버에게는 필드 자체가 없다.

#### POST /communities — 생성

```json
// 요청
{ "name": "만나 개발팀" }

// 201
{ "id": 12, "name": "만나 개발팀", "inviteCode": "k7mQ2xR9tB" }
```

⚠️ **만든 사람의 `community_members` 행은 `status='active'`, `role='leader'`를 명시적으로
넣는다.** `status`의 DEFAULT가 `'pending'`이라 그대로 두면 **생성자가 자기 방에 승인 대기로
갇힌다.** 승인해 줄 리더가 그 자신이므로 빠져나올 수 없다.

#### GET /communities/{id} — 대문

```json
{
  "id": 3,
  "name": "2026-2기 수요 새가족반",
  "myRole": "leader",
  "inviteCode": "k7mQ2xR9tB",
  "prayerPartner": { "userId": 12, "name": "김현정" },
  "members": [
    { "userId": 12, "name": "김현정", "profileImageUrl": null, "role": "member" }
  ],
  "pendingMembers": [
    { "userId": 20, "name": "이수진" }
  ]
}
```

- **`inviteCode`와 `pendingMembers`는 리더에게만.** 멤버 응답에는 필드가 아예 없다.
- `prayerPartner`는 **이 방의** 짝이다. 메인의 기도짝(`GET /pray/summary`)은 내 모든 방의 짝
  중 하나라 값이 다르다 — 같은 것으로 보고 한쪽을 지우면 안 된다.
  배정 스케줄러가 Phase 3이라 **당분간 항상 `null`**이고, 화면은 그 상태를 감당해야 한다.
- **신청 시각(`requestedAt`)을 주지 않는다.** `community_members`에 있는 시각 컬럼은
  `joined_at`인데 `pending` 행은 아직 합류하지 않아 의미가 어긋나고, MVP의 승인 화면은
  이름만 있으면 된다. 필요해지면 컬럼을 제대로 만들고 그때 넣는다.
- **내가 이 방의 `pending`이면 `404`.** 403이 아닌 이유는 공통 규약에 있다.
- 공지사항·갤러리는 없다(D-1003). 갤러리는 오브젝트 스토리지가 새로 필요하다.

#### PATCH /communities/{id} — 이름 변경 (리더)

```json
{ "name": "2026-3기 수요 새가족반" }
```

계층은 이름 문자열로만 표현한다 — `parent_id`가 없다(`06_ERD.md`).

#### POST /communities/{id}/invite-code — 재발급 (리더)

```json
// 204 아님. 새 코드를 바로 써야 하므로 돌려준다.
{ "inviteCode": "p3Wn8kL5vC" }
```

**이전 코드는 즉시 무효**가 된다. 만료는 두지 않고 재발급만 한다(D-1708) — 승인이 있어서
코드가 새도 피해가 "가입 신청이 하나 뜬다"로 줄기 때문이다.

#### GET /invites/{code} — **비로그인**

```json
{ "communityName": "2026-2기 수요 새가족반" }
```

- **방 이름만 준다.** 어디 들어가는지 모른 채 로그인을 요구하면 이탈하므로 먼저 보여주되
  (D-1005), 그 이상은 로그인 전에 노출할 것이 아니다. 인원 수도 주지 않는다.
- 없는 코드이거나 재발급으로 무효가 된 코드면 `404`.

#### POST /invites/{code}/requests — 가입 신청

```json
// 201
{ "communityId": 3, "status": "pending" }
```

- **자동 가입이 아니다.** 로그인 복귀 후 버튼을 한 번 더 누르게 한다(D-1005) — 잘못 누른
  링크를 되돌릴 수 없기 때문이다.
- 이미 `pending`이거나 `active`면 `409`.

#### POST /communities/{id}/members/{userId}/approve — 승인 (리더)

`204`. 대상이 `pending`이 아니면 `409`.

⚠️ **승인 결과를 푸시로 알리지 않는다.** 알림 도메인이 Phase 3다(D-1707). 리더 쪽 대기 표시도
멤버 목록의 배지뿐이다 — D-903이 똑같은 자리에서 한 번 데였다.

#### DELETE /communities/{id}/members/{userId} — 거절 · 강퇴 · 나가기

`204`. 호출할 수 있는 사람은 **리더**이거나 **자기 자신**뿐이고, 그 외에는 `403`.

⚠️ **마지막 리더는 나갈 수 없다 — `409`.** 리더가 없는 방에는 승인할 사람이 없어 아무도 새로
들어오지 못한다. MVP에 리더 위임이 없으므로(D-1707) 방이 영구히 잠긴다.

### Pray

#### 누가 누구를 볼 수 있는가 (모든 `/pray` 응답의 전제)

두 층으로 갈린다. **섞으면 안 된다.**

1. **사람이 보이는 조건** — 나와 **`active`로 같은 공동체에 속한** 사람. `pending`인 쪽이
   있으면 어느 방향으로도 보이지 않는다.
2. **그 사람의 기도제목이 보이는 조건** — 그 사람이 **나와 공유하는 공동체에 올린** 것.

⚠️ **그래서 "그 사람의 최신 기도제목"이 아니라 "내가 볼 수 있는 것 중 최신"이다.** 김현정이
어제 A방(내가 없는 방)에, 지난주 B방(내가 있는 방)에 올렸다면 **나에게 보이는 것은 지난주
것**이다. `ORDER BY created_at DESC LIMIT 1`을 `sharing_communities` 조인 **뒤에** 걸어야 한다.
조인 전에 걸면 남의 방 글이 잡혔다가 사라져 카드가 비어 보인다.

기도제목이 하나도 안 보이는 사람도 **카드는 만든다**(D-903). 조용한 사람이 기도에서 배제되면
안 되고, 그 빈 카드가 곧 작성 유도의 자리다.

⚠️ **나 자신은 넣지 않는다.** 중보기도는 남을 위한 것이고, `POST /pray/{userId}`가 자기
자신이면 `400`이라 **카드는 보이는데 버튼이 안 눌리는 상태**가 된다. 내 기도제목은
`/pray/requests/me`가 따로 있다.

#### GET /pray/room — 중보기도실

화면이 **구획 셋**으로 나뉘므로 응답도 그렇게 준다. 평평한 배열 하나를 정렬만 해서 주면
**클라이언트가 "이 사람이 기도짝인가"를 다시 판정해 경계를 계산해야 한다** — 서버가 이미 아는
규칙을 두 곳에 두게 된다.

```json
{
  "partners": [
    {
      "userId": 12,
      "name": "김현정",
      "profileImageUrl": null,
      "communities": [ { "id": 3, "name": "2026-2기 수요 새가족반" } ],
      "partnerIn": [ { "id": 3, "name": "2026-2기 수요 새가족반" } ],
      "request": {
        "body": "1. 나의 한정적인 생각으로...\n2. 나를 둘러싼 공동체와...",
        "createdAt": "2026-08-27T09:14:00Z",
        "daysAgo": 4
      },
      "prayedByMeToday": false
    }
  ],
  "members": [
    {
      "userId": 20, "name": "이수진",
      "communities": [ { "id": 3, "name": "2026-2기 수요 새가족반" } ],
      "request": null,
      "prayedByMeToday": true
    }
  ]
}
```

| 구획 | 필드 | 무엇 |
|---|---|---|
| 상 | `partners` | 이번 주 기도짝. 공동체마다 한 명이라 **모임이 3개면 3명** |
| 중 | `members` | 볼 수 있는 나머지 사람 — **기도짝은 뺀다** |
| 하 | (없음) | 익명 기도제목. **MVP 제외**(D-906) |

- ⚠️ **`members`에서 기도짝을 반드시 뺀다.** 안 빼면 같은 사람이 두 구획에 나온다.
- ⚠️ **익명 구획은 필드 자체를 만들지 않는다.** 지금 넣으면 항상 빈 배열이고, 붙일 때는
  `visibility='anonymous'` 조회 규칙이 새로 필요해 어차피 설계가 따로 온다(D-906).
  나중에 `anonymous` 필드를 **더하는** 것은 기존 클라이언트를 깨지 않는다.
- ⚠️ **`partners`는 Phase 3까지 항상 빈 배열이다.** 배정 스케줄러가 Phase 3이라 `prayer_partners`에
  행이 생기지 않는다. 화면은 그 구획을 **통째로 숨겨야** 한다 — 제목만 덩그러니 남으면 안 된다.
- `partnerIn`은 `partners`에만 있다. 한 사람이 두 방에서 모두 내 짝일 수 있어 배열이다.
- **사람 단위로 합친다**(D-905). 여러 방에 걸쳐도 카드는 하나이고 `communities`가 여럿이 된다.
- **구획 안에서 방으로 다시 나누지 않는다**(D-904). 시안(`Pray Page.png`)의 공동체별 목록은
  이 결정 이전 것이다.
- `request: null` = 기도제목이 없거나 내게 보이는 것이 없는 사람. **기도는 누를 수 있다.**
- `daysAgo`는 서버가 계산해 넣는다 — 클라이언트 시계를 믿지 않는다.
- **페이징 없다.** MVP 규모에서 수십 명이고, 정렬 기준이 서버 계산이라 커서를 얹으면
  설계가 커진다. 필요해지면 그때 붙인다.

**정렬은 구획 안에서만 적용한다** (D-1703 → D-1907 → D-1908 → **D-1909에서 현재 형태로**)

```sql
ORDER BY
  prayed_today_by_me ASC,              -- 1. 오늘 내가 아직 안 한 사람 먼저
  latest_request_at DESC NULLS LAST,   -- 2. 기도제목이 최신인 사람 먼저
  last_prayed_by_me ASC NULLS FIRST,   -- 3. 내가 오래 안 한 사람 먼저
  u.id ASC                             -- 4. 동점은 언제나 같은 순서로
```

**키마다 주어가 다르다.** 1·3은 나, 2·4는 그 사람이다.

```sql
-- 1. prayed_today_by_me: 오늘 내가 이 사람을 위해 기도했나. 목록을 크게 둘로 가른다.
EXISTS (SELECT 1 FROM prayer_logs
        WHERE pray_by = :me AND prayed_for_user_id = u.id AND prayed_on = CURRENT_DATE)

-- 2. latest_request_at: 응답의 request.createdAt과 같은 값이라 새로 계산할 것이 없다.
--    TIMESTAMPTZ(초 단위)라 동점이 사실상 없다 — 기도제목이 있는 사람은 여기서 다 갈린다.
--    sharing_communities 조인 **뒤에** 잡은 최신 한 건이어야 한다
--    (= "그 사람의 최신"이 아니라 "내가 볼 수 있는 것 중 최신").

-- 3. last_prayed_by_me: 내가 이 사람에게 마지막으로 기도한 날. NULL이면 한 번도 안 했다.
SELECT max(prayed_on) FROM prayer_logs
WHERE pray_by = :me AND prayed_for_user_id = u.id
```

- **3번이 `recent_received`(그 사람이 모두에게서 받은 수)를 대체했다** (D-1908).
  받은 수는 전원에게 **같은 순서**를 줘서, 모두가 같은 사람을 맨 위에서 보고 거기에 기도가
  몰렸다가 다음 사람으로 옮겨 가는 쏠림을 만든다. 내 기준으로 바꾸면 목록이 사람마다 달라지고,
  각자가 자기가 소홀했던 사람을 챙기는 것의 합이 오히려 더 고르게 퍼진다.
  덤으로 **"최근 7일"이라는 근거 없는 숫자가 사라졌다** — `max(prayed_on)`은 창을 안 쓴다.
- **2번은 `TIMESTAMPTZ`라 거의 다 갈린다.** 그래서 3번은 실질적으로 **기도제목이 없는
  사람들끼리의 순서**를 정한다. D-903이 지켜지는 자리가 거기다 — 조용한 사람도 내가 오래
  안 챙겼으면 그 무리의 맨 위로 올라온다. 3번을 빼고 `u.id`로만 두면 그 무리의 순서가
  영구히 고정돼, D-1703이 이름순을 반려한 것과 같은 함정에 빠진다.
- **3번의 `prayed_on`은 `DATE`라 같은 날이면 동점이다.** 4번이 그것을 받는다.
- 이름순을 쓰지 않는 이유: 앞사람만 계속 기도받아 "모두가 공평히 기도받는다"(D-303)가 무너진다.
  **최신순은 이름순과 다르다** — 고정이 아니라 업데이트하면 올라가므로 순환한다.
- ⚠️ **오늘 기도한 뒤 그 사람이 기도제목을 바꿔도 1순위는 안 풀린다** (D-1910). 하루 한 번이
  `prayer_logs`의 UNIQUE 제약이고, 체크의 뜻은 "이 글을 읽었다"가 아니라 "오늘 이 사람을 위해
  기도했다"이다 — 단위가 사람이라(D-303) 제목이 바뀌어도 그 사실은 변하지 않는다.
  그날 안에 올라온 급한 기도제목을 알리는 일은 **알림 도메인(Phase 3)**의 몫이지 정렬의 몫이 아니다.
- ⚠️ **마지막 키가 없으면 안 된다.** 앞 순위가 같은 사람이 흔한데, 타이브레이커가 없으면
  같은 조건에서도 요청마다 순서가 뒤집힌다.
- ⚠️ **기도짝은 정렬 키가 아니라 구획이다.** `ORDER BY`에 "기도짝인가"를 넣어 한 목록의 맨 위로
  올리는 방법도 있지만, 그러면 클라이언트가 어디까지가 기도짝인지 알 수 없어 제목을 못 붙인다.
- **인덱스가 하나 필요하다**: `idx_prayer_logs_by_me(pray_by, prayed_for_user_id, prayed_on)`.
  1번과 3번이 둘 다 `pray_by = :me`로 시작하는데, 기존 `idx_prayer_logs_target_day`는
  "받는 사람" 기준이라 그 필터를 못 탄다.

**⚠️ 순서 고정은 클라이언트가 한다 (서버는 무상태)**
서버는 부를 때마다 위 규칙으로 새로 정렬한다. 그런데 **"기도했어요"를 누르면 그 사람의
1순위 키가 뒤집혀** 목록으로 돌아왔을 때 방금 기도한 사람이 아래로 사라진다. 무엇을 했는지
확인할 수 없고 스크롤 위치도 의미를 잃는다 — 성경 리더의 스크롤 튐(D-1101~1105)과 같은
종류의 문제다.

- 목록에 처음 들어올 때 받은 **`userId` 순서를 구획별로 sessionStorage에 둔다.** 사람 상세를
  갔다 돌아오면 그 순서를 그대로 쓴다. 구획 사이를 옮겨 다니는 사람은 없으므로 구획마다
  독립적으로 고정하면 된다.
- **다른 탭(성경·공동체·홈)에 갔다가 기도실로 다시 들어오면 버리고 새로 부른다.**
  탭 단위 수명이 "이번에 기도하는 흐름"과 정확히 맞는다 — 쿠키가 아니라 sessionStorage인
  이유도 D-1506과 같다.
- **순서는 고정이어도 카드 표시는 갱신한다.** `prayedByMeToday`가 그것을 위해 있다.

#### GET /pray/requests/{userId} — 상세 화면

```json
{
  "userId": 12,
  "name": "김현정",
  "communities": [ { "id": 3, "name": "2026-2기 수요 새가족반" } ],
  "request": { "body": "1. ...", "createdAt": "2026-08-27T09:14:00Z", "daysAgo": 4 },
  "prayedByMeToday": false
}
```

목록의 항목 하나와 같은 모양이다. 목록을 들고 들어가면 이 호출이 필요 없지만, **링크로 바로
들어오거나 새로고침하면 필요하다.** 볼 수 없는 사람이면 `404`.

#### POST /pray/{userId} — "기도했어요"

`204`.

- `prayer_logs`에 `(prayed_for_user_id, pray_by, prayed_on=오늘)`을 넣는다.
  `UNIQUE` 제약이 있어 **두 번 눌러도 하나다 — 멱등하다.** 중복은 에러가 아니라 성공으로 받는다.
- 자기 자신이면 `400`(자기참조 금지 제약). 볼 수 없는 사람이면 `404`.
- **어느 기도제목을 보고 눌렀는지 기록하지 않는다.** 기도의 단위가 제목이 아니라 사람이라
  `prayer_logs`에 `sharing_id`가 아예 없다.
- ⚠️ **응답에 카운트를 돌려주지 않는다.** 카운트는 어제 기준이라(D-901) 오늘 누른 것이 오늘
  보이는 숫자를 바꾸지 않는다. **돌려줄 새 숫자가 없다.**
- 상세 화면의 "취소하기"는 **그냥 뒤로 가기**다. 기록을 지우는 것이 아니므로 대응하는
  `DELETE`가 없다.

#### GET /pray/summary — 메인 최상단

메인의 "사랑으로 나누세요" 카드 **두 줄을 한 번에** 준다 — 어제 받은 수와 이번 주 기도짝.
호출을 나누면 한 카드를 그리는 데 두 번을 부른다.

```json
{
  "yesterdayCount": 5,
  "partner": { "userId": 12, "name": "현솔", "communityName": "2026-2기 수요 새가족반" },
  "partnerTotal": 3
}
```

```sql
SELECT count(*) FROM prayer_logs
 WHERE prayed_for_user_id = :me AND prayed_on = CURRENT_DATE - 1;
```

- **0이면 "0명이 기도했어요"를 쓰지 않는다**(D-1705). 0은 틀린 숫자가 아니라 *"어제의 기도로
  오늘을 산다"*가 성립하지 않는 상태이고, 앱 밖의 기도까지 세는 숫자도 아니다.
  그 자리를 **기도 유도로 바꾼다** — 받은 것이 없을 때 주는 쪽으로 돌리는 것이 중보기도의
  취지와 맞고, 실제로 0을 깨는 유일한 경로다(내가 누르면 상대에게 앱을 열 이유가 생긴다).
- **유도 문구("나의 기도가 필요한 곳이 있어요")는 API가 관여하지 않는다.** 고정 텍스트 +
  중보기도실 링크다. 특정인을 지목해 내려주면 "누구를 고를 것인가" 규칙이 서버에 하나 더
  생기는데, 그 규칙은 이미 `/pray/room`의 구획과 정렬에 있다. **같은 규칙을 두 곳에 두지 않는다.**
- 기도한 사람은 익명이라 이름을 주지 않는다(D-902). `pray_by`는 저장하되 노출하지 않는다.

**`partner` — 기도짝이 여럿일 때 누구를 보여주나**

기도짝은 공동체마다 한 명이라 모임이 3개면 3명이다. 메인에는 **오늘 내가 아직 기도하지 않은
짝** 하나를 보여준다. 동점이면 `/pray/room`의 2·3순위(적게 받은 순 → `id` 순)로 가른다.

- **랜덤으로 고르지 않는다.** 새로고침마다 이름이 바뀌면 *"이번주 기도짝"* 이라는 말 자체가
  거짓이 된다. 이 규칙은 바뀌긴 하되 **바뀌는 데 이유가 있다** — 내가 기도했기 때문이다.
  D-1705에서 랜덤 문구를 반려한 것과 같은 판단이다.
- 눌러 들어가면 그 사람 상세가 아니라 **중보기도실 목록**으로 보낸다. 기도짝은 거기 맨 위
  구획에 있으므로 어차피 바로 보인다.

세 가지 상태를 구분해야 한다. `partner`만으로는 부족해서 `partnerTotal`이 있다.

| 응답 | 뜻 | 화면 |
|---|---|---|
| `partnerTotal: 0` | 짝이 없다 — **Phase 3까지 항상 이 상태** | 기도짝 줄을 통째로 숨긴다 |
| `partner: {...}` | 오늘 아직 기도 안 한 짝이 있다 | "이번주 기도짝은 ○○님이에요" |
| `partner: null`, `partnerTotal: 3` | 짝 셋 모두 오늘 기도했다 | "이번주 기도짝 모두를 위해 기도했어요" |

⚠️ **`partnerTotal: 0`과 `partner: null`은 다르다.** 둘을 한 필드로 합치면 "짝이 아직 없음"과
"다 기도함"이 구분되지 않아, 배정 전인데 "모두를 위해 기도했어요"가 뜬다.

⚠️ **가입 첫날은 `yesterdayCount: 0` + `partnerTotal: 0`이다.** 카드의 두 줄이 다 비는 유일한
상태이고, 실제로 모든 신규 사용자가 여기서 시작한다. 화면은 이 경우를 반드시 감당해야 한다.

#### GET /pray/requests/me — 내 기도제목 이력

```json
{
  "requests": [
    { "id": 88, "body": "1. ...", "createdAt": "2026-08-27T09:14:00Z",
      "communities": [ { "id": 3, "name": "2026-2기 수요 새가족반" } ] }
  ]
}
```

최신순. **이력 화면 자체는 MVP에서 빼지만**(D-1706) 저장이 append-only라 데이터는 이미
쌓이므로 주소를 지금 맞게 잡아 둔다. 작성 폼은 이 목록의 **첫 항목**을 채워 넣는다.

#### POST /pray/requests/me — 기도제목 업데이트

```json
// 요청
{ "body": "1. ...\n2. ...", "communityIds": [3, 7] }

// 201
{ "id": 91, "body": "1. ...", "createdAt": "2026-08-31T02:10:00Z",
  "communities": [ { "id": 3, "name": "..." }, { "id": 7, "name": "..." } ] }
```

- **"수정"이 아니라 "업데이트"다**(D-1706). 기존 행을 고치지 않고 **새 행을 쌓는다.** 화면에는
  이어지는 하나로 보이고, `created_at`이 갱신되므로 카드의 "○일 전"이 저절로 맞는다.
- `communityIds`는 **내가 `active`인 방만** 허용한다. 아니면 `403`.
- **빈 배열은 `400`.** 아무 방에도 올리지 않은 기도제목은 누구에게도 보이지 않아, 쓴 사람은
  올렸다고 믿는데 아무도 기도하지 않는 상태가 된다.
- **`visibility`를 받지 않는다.** 익명 기도제목은 MVP에서 뺐으므로(D-906) 항상 `'public'`이다.
  나중에 붙일 때 필드를 추가한다.
